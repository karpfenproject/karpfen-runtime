# 3.1 Execution semantics

The rules of this chapter say what the runtime does with a state machine while an environment runs. They cover these
points.

- which states are active
- when the ENTRY and DO blocks run
- which transition fires
- what the actions do to the model
- how events travel

How the constructs are written is the subject of
[2.3 KStates](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md). Every
table of ticks in this chapter was taken from a run of the runtime with the state machines that the chapter shows.

## 3.1.1 Example state machine

Most examples work with the metamodel and the model of the lamp example project of the IDE, in the folder
`examples/lamp`. The metamodel has a type `Lamp` with a property `mode`, a `Bulb` in the relation `bulb` and a
`Switch` in the relation `control`. The model holds the lamp `lamp`, its bulb `bulb` and the wall switch
`wallSwitch`. The event definitions declare the events `press` and `dim`. Of the two, only `dim` carries a property, the
boolean `bright`.

```kmeta
type "press" "Presses the wall switch" {
}
type "dim" "Turns the dimmer one step" {
    prop("bright", "boolean")
}
```

In this chapter the lamp runs a state machine that is simpler than the one of the lamp example project. Its state
`on` has only the two inner states `full` and `dimmed`, each of which gives the bulb a fixed number of watts.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            ENTRY {
                SET("mode", "off")
                SET("bulb->lit", "false")
                SET("bulb->watts", "0")
            }
        }
        STATE "on" {
            ENTRY {
                SET("mode", "on")
                SET("bulb->lit", "true")
            }
            STATE "full" {
                ENTRY { SET("bulb->watts", "40") }
            }
            STATE "dimmed" {
                ENTRY { SET("bulb->watts", "20") }
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "full" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "dimmed" -> "full" {
            CONDITION {
                EVENT("switch", "dim")
                VALUE("event->bright")
            }
        }
    }
}
```

The wall switch `wallSwitch` has a state machine of its own that reacts to the same `press` events as the lamp.

```kstates
STATEMACHINE ATTACHED TO "Switch" {
    STATES {
        INITIAL STATE "down" { }
        STATE "up" {
            ENTRY {
                SET("position", "up")
                APPEND("presses", "up")
            }
        }
        STATE "back down" {
            ENTRY {
                SET("position", "down")
                APPEND("presses", "down")
            }
        }
    }
    TRANSITIONS {
        TRANSITION "down" -> "up" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "up" -> "back down" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "back down" -> "up" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

## 3.1.2 Ticks

An environment runs in ticks, numbered from 1 at the first start. A start after a stop goes on with the next number.
Everything else that a stop keeps as it was is listed in
[3.1.13.9 Stop and start, forcing and clients](#31139-stop-and-start-forcing-and-clients).

In one tick the runtime takes these steps in this order.

1. It applies the states that clients forced since the last tick with `setActiveState` of
   [3.1.11 Forcing a state](#3111-forcing-a-state).
2. While the feature EventRecording of [3.2 Runtime features](3.2-features.md) records, it hands the events that
   clients sent since the last tick to the state machines and records them under the number of this tick. While the
   feature EventInjection injects, it hands over the injected events that are due.
3. With the feature TickLimit on, it counts this tick for every active state.
4. It removes the events whose time to live is over.
5. It runs one step of every state machine instance, one after the other, in the order of
   [3.1.13.2 The order of the steps](#31132-the-order-of-the-steps). The attached state machines come first, in the
   order of their first upload, and the instances of attachable state machines after them. An instance that ended
   earlier in the tick does no step. With the feature TrueParallel on, the branches of a split state machine do their
   steps at the same time. This step of the tick ends when all of them are done.
6. It reports the active states of every state machine whose active states changed in this tick. In the first tick
   after the first start it reports those of every state machine.
7. It lets the instances that ended in this tick leave and the instances that rules asked for join.
   [3.1.13.3 When instances join and leave](#31133-when-instances-join-and-leave) explains what this does to the order
   of the steps.

The tick delay, in milliseconds, is the shortest time from the start of one tick to the start of the next one. With a
tick delay of 500 ms, a tick that takes 30 ms is followed by a wait of 470 ms, while a tick that takes longer than the
tick delay is followed by the next tick at once. An environment takes its tick delay from `setTickDelay`. If no client
sets it, the option `engine.defaultTickDelayMs` of [3.3 Running the runtime](3.3-running-the-runtime.md) applies.

Without EventRecording, the events that clients send reach the state machines as soon as they arrive. Because the
runtime looks for new events every 10 ms, also in the middle of a tick, a state machine late in the order can see an
event in a tick in which an earlier one did not see it.

All state machines of one environment run one after the other on a single thread. While one of them waits for Python
in an `EVAL`, all others of its environment wait as well. With the feature
[3.2.9 TrueParallel](3.2-features.md#329-trueparallel) on, each branch of a split gets a thread of its own.

## 3.1.3 Active states

The active states of a state machine form a stack. It starts with a state of the top level and goes down, from each
state to the state inside it, to the innermost active state. When the lamp is in `dimmed`, its stack is `on`,
`dimmed`. A state machine has one stack as long as it is not split, and one stack per branch after a split of
[3.1.8 Splits and joins](#318-splits-and-joins). Clients receive the stack in the message `stateChange` of the
[WebSocket of the runtime](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/websocket.md#statechange).

### 3.1.3.1 Initial state

At the start the runtime builds the stack level by level. It follows the rule of
[2.3.2.2 The initial state](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2322-the-initial-state),
the same rule that the checks of dsl-tools and of the IDE use. On each level it takes the state that is marked
`INITIAL` or that holds the marked state somewhere inside it. If no state of the level is marked or holds the mark, it
takes the first state of the level. As long as the chosen state has inner states the runtime goes on below it, until it
reaches a state without inner states.

Since the reader of KStates allows exactly one `INITIAL` in a state machine, and reports any other number with the
check `kstates.initial-state-count`, a state machine starts in the marked state and in every state around it,
wherever these stand among their siblings. Because the mark in the following text sits inside `on`, the stack at the
start is `on`, `dimmed`, although `off` is the first state of the top level.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        STATE "off" { }
        STATE "on" {
            STATE "full" { }
            INITIAL STATE "dimmed" { }
        }
    }
    TRANSITIONS { }
}
```

With `INITIAL STATE "on"` and no mark inside `on`, the stack at the start would be `on`, `full`. All states of the
start stack are entered in tick 1, from the outside in.

A start that reaches a container state goes on into its fragment, since a container state counts as a state with
inner states. The same rule holds for every way of entering a container state and is given in
[3.1.14.3 Entering a container state](#31143-entering-a-container-state).

### 3.1.3.2 Entering states

A state that becomes active is entered. Entering a state runs its ENTRY block once. For the states that a transition
enters, the ENTRY blocks run in the tick after the transition, from the outermost to the innermost of them. For the
states of the start stack they run in tick 1.

The DO block of the innermost active state runs once in every tick in which no transition fired before it, the tick in
which the state was entered included. The DO blocks of the outer states do not run as long as an inner state is
active.

Since states have no exit blocks, nothing runs when a state is left.

For every way of entering a state and every kind of target, [3.1.15 Where the engine goes](#3115-where-the-engine-goes)
gathers where the stack goes and in which tick the ENTRY blocks run.

### 3.1.3.3 Steps of a tick

The step of a state machine in a tick ends with the first transition that fires. Until then the state machine does
the following, in this order.

1. With the feature History on, it notes the active inner states of every state that has a history.
2. It enters the states not yet entered, from the outside in. Before each ENTRY block a breakpoint on the entry of the
   state can halt the run. After each ENTRY block that has at least one action, it looks over the whole stack for a
   transition that can fire. If one fires, the ENTRY blocks of the states further inside do not run.
3. With the feature TickLimit on, it fires the timeout of a state whose time is over.
4. With the feature History on, it leads on into the remembered inner state when the innermost active state has a
   history and something to remember.
5. It runs the DO block of the innermost active state.
6. It looks for a transition that can fire and fires it.
7. When no transition fired, it consumes the events that a transition of an active state waited for but could not
   use. These are the events of the second way of [3.1.7.3 Consumption](#3173-consumption).

In the following run of the lamp and the switch, a press was sent before tick 3, a `dim` with `bright` false before
tick 5 and another press before tick 7.

| Tick | Event | lamp | wallSwitch |
|---|---|---|---|
| 1 | | ENTRY of `off` runs. Stack `off` | Stack `down` |
| 2 | | Stack `off` | Stack `down` |
| 3 | press | `"off" -> "full"` fires. Stack `on`, `full` | `"down" -> "up"` fires. Stack `up` |
| 4 | | ENTRY of `on` and of `full` run. `watts` is 40 | ENTRY of `up` runs |
| 5 | dim | `"full" -> "dimmed"` fires. Stack `on`, `dimmed` | Stack `up` |
| 6 | | ENTRY of `dimmed` runs. `watts` is 20 | Stack `up` |
| 7 | press | `"on" -> "off"` fires. Stack `off` | `"up" -> "back down"` fires |
| 8 | | ENTRY of `off` runs. `watts` is 0 | ENTRY of `back down` runs |

After tick 8 the list `presses` of the switch is `["up", "down"]`.

A transition can also fire right after an ENTRY block. In the next run the `dim` arrives while the lamp is off and
waits there. Because it fires right after the ENTRY block of `on`, the ENTRY block of `full` further inside never
runs.

| Tick | Event | lamp |
|---|---|---|
| 2 | dim | Stack `off`. The event stays, because no transition of `off` waits for `dim` |
| 4 | press | `"off" -> "full"` fires. Stack `on`, `full` |
| 5 | | ENTRY of `on` runs, then `"full" -> "dimmed"` fires on the waiting `dim`. Stack `on`, `dimmed` |
| 6 | | ENTRY of `dimmed` runs. `watts` is 20 |

## 3.1.4 Transitions

### 3.1.4.1 Which transition fires

The runtime looks for a transition from the innermost active state outwards. For each state it tries the `TRANSITION`
and `SPLIT` that start at the state, in the order of the file. The first one whose condition holds fires. At most one
transition fires per stack in one step.

Since the search goes outwards through the whole stack, a transition that starts at an outer state applies while any
of its inner states is active. The transition `"on" -> "off"` switches the lamp off from `full` as well as from
`dimmed`. When a transition of an inner state and one of an outer state could both fire, the one of the inner state
wins because it is tried first.

A state machine that is split into branches tries its `JOIN` transitions before all others.
[3.1.8 Splits and joins](#318-splits-and-joins) says when a join fires.

### 3.1.4.2 Conditions

A transition without `CONDITION` block fires whenever it is tried. A condition holds when all of its clauses hold.

`EVENT("switch", "press")` holds when an event named `press` in the domain `switch` is there for this state machine.
When several such events are there, the runtime tries them from the oldest to the newest and takes the first one for
which the other clauses hold. The other clauses see this event as `event`. A condition has at most one `EVENT`
clause. Wherever it stands among the clauses, the runtime treats it as the first one.

`VALUE("path")` holds when the path leads to the boolean `true` or to the string `true`, written in any mix of upper
and lower case. `VALUE("true")` always holds and `VALUE("false")` never does. A path starts either at the object of
the state machine, for example `VALUE("bulb->lit")`, or at the event, for example `VALUE("event->bright")`. If the
path leads nowhere, the clause is false.

`EVAL { ... }` holds when its Python code returns `True`. Any other result makes it false, as does an error. The
runtime writes such an error to its console. [3.1.6.4 Errors in code](#3164-errors-in-code) lists the errors that
code can give.

A condition without an `EVENT` clause sees as `event` the scoped event of
[3.1.7.5 Scoped events](#3175-scoped-events), the event that led into the current state.

`DONE` holds when the container state that the transition leaves rests on a final state of its fragment. The exact
rule, also for splits and joins, is given in [3.1.14.5 Final states and DONE](#31145-final-states-and-done).

In the lamp, `"dimmed" -> "full"` needs a `dim` whose `bright` is true. A `dim` with `bright` false that arrives in
`dimmed` fires nothing and is consumed. This happens in tick 6 of the next run.

| Tick | Event | lamp |
|---|---|---|
| 2 | press | `"off" -> "full"` fires |
| 3 | | ENTRY of `on` and `full` run |
| 4 | dim, bright false | `"full" -> "dimmed"` fires |
| 5 | | ENTRY of `dimmed` runs |
| 6 | dim, bright false | Nothing fires. The event is consumed |
| 7 | dim, bright true | `"dimmed" -> "full"` fires |
| 8 | | ENTRY of `full` runs. Stack `on`, `full` |

### 3.1.4.3 Where a transition leads

After a transition the stack is the path from the top level down to the target state. The runtime does not go down
into the inner states of the target. After `"full" -> "on"` the stack is `on`. From then on the DO block of `on`
runs, because `on` is now the innermost active state. The one exception is a container state: the runtime goes down
into its fragment as shown in [3.1.14.3 Entering a container state](#31143-entering-a-container-state).

The runtime enters the states of the new stack that were not on the old stack. A transition from a state to itself,
and a transition from a state to one of its outer states, enter the target again together with the state around it.
With the stack `on`, `full`, the transition `"full" -> "full"` enters `on` and `full` again. `"full" -> "on"` enters
`on` again, as does `"on" -> "on"` on the top level.

### 3.1.4.4 NOT LOOPING

A transition marked `NOT LOOPING` does not fire if it was the last transition that fired in its stack. The runtime
then tries the next one. The lamp with the following state machine runs in a circle of three ticks.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            ENTRY { SET("mode", "on") }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" { }
        TRANSITION "on" -> "on" NOT LOOPING { }
        TRANSITION "on" -> "off" { }
    }
}
```

| Tick | lamp |
|---|---|
| 1 | `"off" -> "on"` fires |
| 2 | ENTRY of `on` runs, then `"on" -> "on"` fires |
| 3 | ENTRY of `on` runs. Since `"on" -> "on"` was the last transition, `"on" -> "off"` fires |
| 4 | `"off" -> "on"` fires |

## 3.1.5 Actions

### 3.1.5.1 Blocks and errors

An ENTRY or DO block runs its actions in order. The changes that a block makes reach the clients together once the
block is done, in the messages `objectChanged` and `objectDeleted` of the
[WebSocket of the runtime](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/websocket.md#pushed-messages).

An action that fails stops the rest of its block, while the changes of the actions before it stay. The run goes on
after the runtime has written the error to its console and to the trace log. In the following ENTRY block the second
action fails because `Bulb` has no property `colour`. By then the first action has set `mode` to `broken`. `lit` stays
as it was, because the third action does not run.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            ENTRY {
                SET("mode", "broken")
                SET("bulb->colour", "red")
                SET("bulb->lit", "true")
            }
        }
    }
    TRANSITIONS { }
}
```

The trace log gets this line.

```text
ACTION_ERROR: Error in onEntry for state 'off': 'colour' on 'Bulb' is not a scalar property (use SETOBJ for relations)
```

### 3.1.5.2 Values on the right side

The value of an action is a string, an `EVAL` block or a `MACRO` call.

A string is read according to the type of the property it is written to.

| Type of the property | The string |
|---|---|
| `number` | Is read as a number: `"40"` is the number 40. A string that is no number is an error of the action |
| `boolean` | Must be `true` or `false` |
| `string` | Is taken as it is |

An `EVAL` block or a `MACRO` call computes the value in the way described in
[3.1.6 EVAL and macros](#316-eval-and-macros). If it returns nothing, the action does nothing.

### 3.1.5.3 Properties and lists

A path names a property, either of the object of the state machine, such as `"mode"`, or of an object that is reached
over relations, such as `"bulb->watts"`.

| Action | What it does |
|---|---|
| `SET("path", value)` | Sets a property that holds one value |
| `APPEND("path", value)` | Adds the value at the end of a list property. A list that has no value yet is created |
| `SETLIST("path", value)` | Replaces the whole list. A string gives a list of one element, an `EVAL` or `MACRO` gives the list it returns |
| `DROPLIST("path")` | Removes the list property |

In this ENTRY block `SETLIST` replaces the list `presses` of the switch with a list of one element, to which `APPEND`
then adds a second one.

```kstates
STATEMACHINE ATTACHED TO "Switch" {
    STATES {
        INITIAL STATE "down" {
            ENTRY {
                SET("position", "down")
                SETLIST("presses", "reset")
                APPEND("presses", "down")
            }
        }
    }
    TRANSITIONS { }
}
```

After the block, `presses` is `["reset", "down"]`.

### 3.1.5.4 Objects and relations

| Action | What it does |
|---|---|
| `SETOBJ("source", "relation", value)` | Sets a relation that holds one object |
| `APPENDOBJ("source", "relation", value)` | Adds an object to a relation that holds a list |
| `DROPOBJ("path")` | Removes an object from the model |
| `SETOBJ(...) ATTACH name`, `APPENDOBJ(...) ATTACH name` | Creates the object with an instance of the attachable state machine `name` |
| `EXCHANGE("path", name)` | Gives the object at the path an instance of the attachable state machine `name` |

The source is the path to the object that owns the relation. In it, both `""` and `"self"` stand for the object of
the state machine.

A `has` relation needs a new object. Its value is an `EVAL` or a `MACRO` that returns the object as a dictionary with
the properties of its type, from which the runtime builds the object. The key of the new object is the entry
`__id__` of the dictionary, or `gen_<Type>_<n>` if the dictionary has no such entry. If `__id__` is the key of an
object that already exists, the dictionary changes that object in place. `SETOBJ` on a `has` relation removes the
object that was there before, together with everything it holds.

A `knows` relation needs an object that exists. Its value is a string with the path from the object of the state
machine to that object, or an `EVAL` or `MACRO` that returns either a dictionary with the `__id__` of the object or
its key as a string.

The type of the object must be the type of the relation. An action also fails when it gives a `has` relation an
existing object or a `knows` relation a new one.

A dictionary with the `__id__` of an existing object changes that object in place wherever an `EVAL` or a `MACRO`
returns it, also when it is nested inside another dictionary. The properties of the object take the values of the
dictionary. Its relations follow these rules.

- A `has` relation in the dictionary afterwards holds the objects that the dictionary lists there. An object that it
  held before and that the dictionary does not list leaves the model with everything it holds, as with `DROPOBJ`.
- In such a `has` relation, a dictionary without `__id__`, or with an `__id__` that no object has, is a new object.
- In a `has` relation, the dictionary cannot list an object that another object holds. Listing it is an error of the
  action.
- A `knows` relation in the dictionary must list objects that exist.

In the following action, `light` is a `knows` relation from the object of the state machine to the lamp. The action
gives the lamp a new bulb and removes the old one.

```kstates
SETOBJ("self", "light", EVAL { return {"__id__": "lamp", "bulb": {"maxWatts": 60, "watts": 0}} })
```

`DROPOBJ` removes the object at the path together with everything it holds. The runtime also removes every `knows`
reference to a removed object. `DROPOBJ` cannot remove the object of its own state machine, whatever path leads to
it. When objects are removed, the state machine instances of all of them end, also those of the objects that a
replacing `SETOBJ` removes. New objects get instances of the state machines their types behave after. `ATTACH` and
`EXCHANGE` give objects other instances.
[3.1.13 State machine management and lifecycle](#3113-state-machine-management-and-lifecycle) says when instances
begin and end.

In the lamp example project the lamp drops its spare bulb when it breaks.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "working" { }
        STATE "broken" {
            ENTRY {
                DROPOBJ("spare")
                SET("mode", "broken")
            }
        }
    }
    TRANSITIONS {
        TRANSITION "working" -> "broken" {
            CONDITION { EVENT("service", "smash") }
        }
    }
}
```

### 3.1.5.5 Raising events

As an action, `EVENT("domain", "name")` raises an event without payload. The event is on the bus at once and has the
time to live of the environment. While state machines later in the order see it in the same
tick, the state machine that raised it sees it the next time it looks for a transition.

Since the switch comes before the lamp in the order, the lamp in the following run reacts in the same tick to the
`press` that the switch raises when it enters `up`.

```kstates
STATEMACHINE ATTACHED TO "Switch" {
    STATES {
        INITIAL STATE "down" { }
        STATE "up" {
            ENTRY {
                SET("position", "up")
                EVENT("switch", "press")
            }
        }
    }
    TRANSITIONS {
        TRANSITION "down" -> "up" {
            CONDITION { EVENT("button", "push") }
        }
    }
}
```

| Tick | Event | wallSwitch | lamp |
|---|---|---|---|
| 2 | push in domain `button` | `"down" -> "up"` fires | Stack `off` |
| 3 | | ENTRY of `up` runs and raises `press` | `"off" -> "full"` fires |
| 4 | | Stack `up` | ENTRY of `on` and `full` run |

### 3.1.5.6 IF IN SCOPE and WITH

`IF IN SCOPE("path", ...) { ... }` runs its actions only when each of its paths leads to a value. A property
whose value is `false` counts as a value too. A path into `event` needs a scoped event that has the property.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            ENTRY {
                IF IN SCOPE("event->bright") {
                    SET("mode", "dimmed by event")
                }
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "dim") }
        }
    }
}
```

Any `dim` switches this lamp on. The ENTRY block of `on` sets `mode` to `dimmed by event` only if the `dim` carries
`bright`.

`WITH MACRO("name", ...) AS "binding" { ... }` computes the macro once and runs the actions in the block. In their
`EVAL` blocks and paths the actions read the result as `$(binding)` and `$(binding->property)`.

## 3.1.6 EVAL and macros

An `EVAL` block holds Python code that ends with `return`. Before the code runs, the runtime replaces every `$(path)`
with the value at the path, written as a Python value. `$(event->bright)` reads the scoped event. A path that cannot be
followed is an error of the `EVAL`, for example `event->bright` while no event is in scope.

In the lamp example project an `EVAL` gives the lamp its watts. Another `EVAL`, in a condition, checks that the bulb
can take 10 watts more.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            ENTRY {
                SET("bulb->watts", EVAL { return $(bulb->maxWatts) })
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION {
                EVENT("switch", "press")
                EVAL { return $(bulb->watts) + 10 <= $(bulb->maxWatts) }
            }
        }
    }
}
```

### 3.1.6.1 Values in code

| Value | In the code |
|---|---|
| Number | A Python number: `40`, `2.5`. A value that is not a number and the infinities become `float("nan")`, `float("inf")` and `-float("inf")` |
| String | A Python string in double quotes: `"say \"hi\""` |
| Boolean | `True` or `False` |
| List | A Python list of these values |
| Object | A dictionary with the entries `__id__`, `__type__`, its properties and its relations |
| No object in a relation that holds one | `None` |

A string reaches the code with exactly its text, whether it comes from a property, from inside an object, from an
argument of a macro or from an event. Inside the quotes the runtime writes the following characters with an escape
and every other character as it is, also characters outside ASCII.

| Character | Written as |
|---|---|
| Double quote | `\"` |
| Backslash | `\\` |
| Line break | `\n` |
| Tab | `\t` |
| Carriage return | `\r` |
| Other control characters | `\x` and two hex digits |

Since the value comes with its quotes, `$(name)` must not be put inside quotes of its own. Two texts are joined with
`+`, for example `"Hello " + $(name)`.

Because `has` and `knows` relations alike are dictionaries again within an object, `$(lamp)` carries the bulb it
holds and the lamps it knows, each with its relations, down to the end. An object that two relations lead to appears
once at each of the two places. If the relations lead back to an object already on the way, as two lamps that know
each other do or a longer circle of `knows` relations, the object cannot be written as a dictionary. The `EVAL` then
fails with a message that names the first object of the loop.

```text
Reference loop through object 'a' cannot be handed to code
```

The runtime writes the model as JSON by the same rule and refuses such a loop there as well. A path that ends at a
property of an object in the loop, such as `$(label)`, still works.

### 3.1.6.2 Results

The code gives its value with `return`. Python hands this value to the runtime as text, in which a dictionary, a list
or a boolean is written as JSON and every other value as Python's `str` of it. How the runtime reads that text depends
on the type that the place of the `EVAL` expects.

| Type | Result |
|---|---|
| `string` | The text as it is, with its spaces and line breaks. `return ""` gives the empty string, `return 4` gives `4` and `return True` gives `true` |
| `number` | A number, also `nan`, `inf` and `-inf`. Anything else is an error of the `EVAL` |
| `boolean` | `True` or `False`. Anything else is an error of the `EVAL` |
| An object type | A dictionary of the form given in [3.1.5.4 Objects and relations](#3154-objects-and-relations) |

Code that returns nothing or `None` gives no result. An action with such code does nothing. If the result does not fit
the type, the error names the expected type and the first 200 characters of what the code gave.

```text
Expected number but got: abc
```

In a condition only `True` makes the clause hold.

What the code prints with `print` or writes to `sys.stdout` or `sys.stderr` never becomes part of the result. After
the call has ended, also after a failed one, the runtime writes it to its console with the key of the object whose
state machine ran the code in front of every line. A `print("debug")` in a state machine on the object `lamp`
appears on the console like this.

```text
[Python lamp] debug
```

Output that passes by `sys.stdout` is dropped, such as that of `os.write(1, ...)`, of a C library or of a child
process. The text that the module `logging` writes and the warnings of Python, such as a `SyntaxWarning` about the
code, appear on the console like the printed text of the call.

### 3.1.6.3 Where code runs

The runtime computes code itself, without Python, when the place of the `EVAL` or the `RETURNS` of the macro expects a
number or a boolean, and when the code, once the values of the paths and of the arguments are written into it, is a
single `return` of an expression built only from these parts.

- numbers, `True` and `False`
- arithmetic and comparisons
- `and`, `or` and `not`
- parentheses

A macro is computed in the same way as an `EVAL`. Code that calls a macro with `@name(arguments)` never qualifies,
because the call is not one of these parts. Neither does the code of a macro that reads into a parameter with
`$(parameter->property)`, because the runtime then puts an assignment in front of the `return`.

In computing, the runtime follows the rules of Python: `-2 ** 2` is -4, `-7 % 3` is 2, `2 or False` is 2 and
`True + True` is 2. Since its own result might differ from the one Python gives in the following cases, the runtime
hands the code to Python after all whenever one of them occurs.

- an expression of these parts that the runtime does not take, such as the chained comparison `1 < 2 < 3`
- a division, a floor division or a modulo by zero
- zero to a negative power
- a negative number to a fractional power
- an infinite number as the result where a number is expected
- a number where a boolean is expected, or a boolean where a number is expected

Python then gives its own result or error. Where the place expects a string or an object, the code always goes to
Python, because only Python knows whether it writes a number as `4` or as `4.0`. Whichever of the two computes the
code, its result and its error are the same.

All other code runs in Python, unless the cache of [3.1.6.6 The result cache](#3166-the-result-cache) holds the
result of the same code text. The runtime calls the first of `python3`, `python` and `py` that it finds on the path.
Each environment has Python processes of its own that stay open from the first call until the environment is dropped.

A variable, a function or an import of one call is not there for the next call, because each call runs in a
namespace of its own. A module that a call imports does stay loaded in the process, though. This is why the next
`import` of it costs almost nothing. For the same reason, whatever code keeps in a module, such as an attribute set on
`math` or the state of `random`, is seen by later calls in the same process. These later calls may come from any
state machine instance of the environment.

Code has to finish everything it starts within its call, such as a thread, a timer or a function that it leaves on a
module for a library to call later, because the runtime empties the namespace of a call when the call returns. A
function that runs after that no longer finds the names of the call. What it prints is discarded, or it is shown
with another call that happens to run at that moment.

Because the standard input of code is empty, `input()` raises `EOFError`. A child process that the code starts
finds no input either.

Without the feature TrueParallel one process runs all the code of the environment, because the instances and their
branches step one after the other. With TrueParallel, whenever more branches wait for Python at the same moment than the
environment has processes, it starts another process and keeps it for later calls. There is no further limit to the
number of processes, because a branch that had to wait for the process of another branch would no longer run in
parallel with it.

### 3.1.6.4 Errors in code

An `EVAL` fails when its code raises an exception, has a syntax error or ends Python. For an exception or a syntax
error the message holds the last line of the Python error.

| Cause | Message |
|---|---|
| An exception or a syntax error, also `sys.exit` | `Python error: ZeroDivisionError: division by zero` |
| Python ends during the call, for example by `os._exit` | `The Python process ended during the call` |

A failed `EVAL` in an action is an error of the action and stops its block by the rule of
[3.1.5.1 Blocks and errors](#3151-blocks-and-errors). The trace log shows the message in a line like this one.

```text
ACTION_ERROR: Error in onEntry for state 'broken': Python error: ZeroDivisionError: division by zero
```

A failed `EVAL` in a condition makes the clause false. The runtime writes the error to its console and, as
`CONDITION_ERROR`, to the trace log. The line names the state that the transition leaves, or for a join all its
source states, separated by commas.

```text
CONDITION_ERROR: Error in a condition of a transition from 'broken': Python error: ValueError: no
```

`sys.exit` is an error of the call that leaves the process running. If the process ends during a call, the next call
starts a new process, in which every module has to be imported again. A call that writes much output to stdout or
stderr is not blocked by it, because Python collects the output until the call ends.

A call has no time limit. A call that does not end, such as `while True: pass`, holds the step of its state machine,
and with it the ticks of the whole environment, until the code ends. If the environment is dropped during such a call,
the runtime waits 5 seconds and then ends all Python processes of the environment. The call then fails.

### 3.1.6.5 Macros

A macro is a named piece of Python code in the `MACROS` block of the file, called with `MACRO("name", "path", ...)`.
Each argument is a path that starts at the object of the state machine, at `event` or at a binding of `WITH`. Its
value is handed to the parameter at the same place in `TAKES`. In the code of the macro, `$(parameter)` is the value
of the parameter and `$(parameter->property)` a property of it. The result must fit the type in `RETURNS`.
Inside Python code, `@name(arguments)` calls another macro of the file as a Python function.

### 3.1.6.6 The result cache

Each environment remembers what Python gave for the code it ran. Before an `EVAL` or a macro goes to Python, the
runtime looks for the same code text among the earlier calls of the environment. If it finds the text, it takes the
stored result without running Python.

The text that is compared is the complete code after the runtime has written the values of the paths into it,
together with the macros the code calls. Two calls share a result only if they would hand Python exactly the same
text, that is, if the code is the same and every value it reads is the same. All state machine instances of an
environment use the same cache. Code that [3.1.6.3 Where code runs](#3163-where-code-runs) lets the runtime compute
itself does not go through the cache.

A call answered from the cache gives the stored result as it is. What the code printed when it ran in Python is not
printed again. Since a failed call is not stored, the same code runs in Python again the next time, fails again and
puts its error into the trace log once more.

The cache matters for code that has effects or whose answer changes by itself. Code that reads the clock, draws a
random number, reads a file or asks a server over the network gets, for the same values, the result of its first run
again. Since the code text of the following condition never changes and only its first result counts, the clause
holds either in every tick or in none.

```kstates
TRANSITION "off" -> "on" {
    CONDITION { EVAL { return __import__("random").random() < 0.5 } }
}
```

Such code needs an environment with caching switched off. For one environment, `POST /setResultCaching` of the
[settings of the HTTP API](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/http-api.md#settings)
with `enabled=false` switches it off before `runEnvironment`. For every environment that does not switch caching on
itself, `engine.resultCaching = false` in `application.conf` does the same. In the answer of
`GET /observatory/metrics`, `resultCaching` tells whether caching is on. The member `calls.cache` counts the calls
answered from the cache.

The cache keeps its results until the environment is dropped, also across a stop and a start. Its two bounds are set
in `application.conf` for every environment and are among the options of
[3.3.4 Configuration](3.3-running-the-runtime.md#334-configuration).

| Bound | Default | Counted as |
|---|---|---|
| `engine.resultCacheMaxEntries` | 10000 | Stored results |
| `engine.resultCacheMaxMegabytes` | 64 | Two bytes per character of the code text and of the result, plus a little for each entry |

When a new result would exceed one of the bounds, the results that were used least recently leave the cache first. A
single result that alone is larger than the memory bound is not stored at all.

### 3.1.6.7 Large values

The time of a call grows with the size of the values in its code, because the runtime writes every value into the
code text and Python reads the whole text before it runs the first line. A value of a few properties adds nothing
that can be measured to a short call. A value with more than about a hundred properties costs several times as much
as the call itself.

The benchmarks of the runtime gave the following times for one call on one machine. The proportions matter more than
the numbers.

| Value in the code | Without the result cache | Answered from the result cache |
|---|---|---|
| A number | 0.06 ms | 0.01 ms |
| A lamp with its bulb, 5 properties in all | 0.06 ms | 0.01 ms |
| A wing with 200 lamps and a bulb each, about 1000 properties | 3.6 ms | 0.4 ms |
| A list of 10000 numbers | 10 ms | 1.0 ms |

The result cache lowers the cost of a large value but does not remove it, because the runtime has to write the values
into the code text before it can look the text up.

Code should therefore get only the values it reads. A path that ends at a property writes one value into the code. A
path that ends at an object writes the object with everything it holds and knows, by the rule of
[3.1.6.1 Values in code](#3161-values-in-code). For an object near the root of the model that is most of the model.
This holds for `$(path)` in an `EVAL` and for the arguments of a macro alike. A macro whose parameter is an object
gets the whole object in every call, also when its code reads a single property of it.

The following macro takes the bulb as an object and reads one property.

```kstates
MACRO "too hot" {
    TAKES("bulb", "Bulb")
    RETURNS("boolean")
    DEFINITION {
        EVAL { return $(bulb->watts) > 60 }
    }
}
```

It is called with `MACRO("too hot", "bulb")`. Every call writes the whole bulb into the code. The next macro does the
same work with the one number it needs and is called with `MACRO("too hot", "bulb->watts")`.

```kstates
MACRO "too hot" {
    TAKES("watts", "number")
    RETURNS("boolean")
    DEFINITION {
        EVAL { return $(watts) > 60 }
    }
}
```

Because a bulb is a small object, the first macro costs little with it. The same macro with a parameter that reaches
200 lamps would pay the 3.6 ms of the table in every call. With the number written in, the code of the second macro is
also a simple expression that the runtime computes itself by the rule of
[3.1.6.3 Where code runs](#3163-where-code-runs).

## 3.1.7 Events

### 3.1.7.1 Domains and names

Every event has a domain and a name, for example the domain `switch` and the name `press`. A transition waits for this
event with `EVENT("switch", "press")`. The domain is free text. Events come from clients over the WebSocket, from
the feature EventInjection and from the action `EVENT`. A client that listens to a domain gets every event of that
domain pushed in the message `domainEvent` of the
[WebSocket of the runtime](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/websocket.md#domainevent).

### 3.1.7.2 Time to live

An event expires when it is older than its time to live. An environment takes the time to live from `setEventTtl` or,
if no client sets it, from the option `engine.defaultEventTtlMs`. A time to live of 0 means that events never expire.
From the moment an event expires it fires no transition.

The runtime frees the memory of expired events at the start of each tick and every 10 ms in between. The oldest events
of a domain are freed as soon as they have expired. An expired event that stands behind a younger one that is still
alive is freed at the latest when the number of events in its domain has doubled.

However many consumed events wait for their time to live to end, they do not make the ticks of the state machine that
consumed them slower. Events with a time to live of 0 stay in memory for the whole run and take a few hundred bytes
each plus their payload. An environment that keeps getting such events grows in memory until it is dropped.

### 3.1.7.3 Consumption

Each state machine sees every event once. An event that the lamp consumed is still there for the switch, since an
event is consumed only for the state machine that consumed it. Within one state machine an event is consumed in one
of three ways.

1. It fires a transition. This holds while the option `engine.eventConsumptionOnFire` is `true`, as it is by default.
   With `false`, the event that fired a transition stays and can fire further transitions in later ticks.
2. No transition fired in the step, and a transition of an active state waits for an event with this domain and name.
   The event is then consumed, even if the other clauses of that transition did not hold. Only the events that were
   there when the step began to look for a transition count. An event that arrives later in the step waits for the
   next step.
3. It expires.

An event that no transition of the active states waits for stays until it expires. If a state that waits for it
becomes active within its time to live, the event fires the transition of that state. The `dim` in the second table
of [3.1.3.3 Steps of a tick](#3133-steps-of-a-tick) waits in `off` in this way.

### 3.1.7.4 Payloads

An event from a client carries a payload as JSON or as KModel text. The runtime reads the payload against the type of
the event definitions whose name is the name of the event. A `dim` with the payload `{"bright": true}` thus gets the
property `bright` with the value `true`.

A payload cannot be read if it is JSON that does not fit the event type, or KModel text with any error of the KModel
reader, such as a syntax error, an unknown property or a value of the wrong type. Such a payload leaves the event
without properties. The runtime writes the errors to its console and the run goes on. The event still fires
transitions by its name, but paths into `event` lead nowhere. The forms of the message that carries an event and its
payload are given under
[Sending events](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/websocket.md#sending-events)
in the description of the WebSocket.

Events raised with the action `EVENT` have no payload. Paths into an event that EventInjection replays lead nowhere
either, because such events are not read against the event definitions.

### 3.1.7.5 Scoped events

The event that fired a transition becomes the scoped event of the target state. While this state is active, its ENTRY
and DO blocks, the paths of its `IF IN SCOPE` and the conditions without `EVENT` clause read this event as `event`. An
inner state that was entered without an event of its own reads the scoped event of the nearest outer state. A state
loses its scoped event when it is left.

### 3.1.7.6 Several state machines

All state machines of an environment share one bus of events. Each of them takes the events it waits for and consumes
them for itself only. That is why the lamp and the switch in the first table of
[3.1.3.3 Steps of a tick](#3133-steps-of-a-tick) both react to the same press in the same tick.

The same holds for every instance. Two objects with instances of the same attachable state machine each consume their
events for themselves. An instance that joins during the run sees the events on the bus whose time to live is not
over.

## 3.1.8 Splits and joins

When a `SPLIT` fires, it replaces the one stack of the state machine with one branch per target state. Each branch has
the stack from the top level down to its target and enters its states in the next tick. The event that fired the
split becomes the scoped event of every target.

While the state machine has branches, it tries every `JOIN` first. A join fires when its condition holds and each of
its source states is active in a different branch. The state machine must also have exactly as many branches as the
join has sources. After the join it has one stack again, the path to the target of the join. The other branches do
no further step in this tick.

When no join fires, each branch does the step of [3.1.3.3 Steps of a tick](#3133-steps-of-a-tick). The
branches step one after the other on the one thread of the environment, in the order of the targets of the split.
With the feature [3.2.9 TrueParallel](3.2-features.md#329-trueparallel) on, they do their steps at the same time, each
on a thread of its own. The stack that clients see holds the stacks of all branches one after the other.

In the following self test the lamp splits into a branch that tests the bulb and one that tests the switch.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "test bulb" {
            ENTRY { SET("bulb->lit", "true") }
        }
        STATE "bulb ok" {
            ENTRY { SET("bulb->lit", "false") }
        }
        STATE "test switch" { }
        STATE "check position" { }
        STATE "switch ok" {
            ENTRY { SET("mode", "tested") }
        }
        STATE "on" {
            ENTRY { SET("mode", "on") }
        }
    }
    TRANSITIONS {
        SPLIT "off" -> "test bulb", "test switch" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "test bulb" -> "bulb ok" { }
        TRANSITION "test switch" -> "check position" { }
        TRANSITION "check position" -> "switch ok" { }
        JOIN "bulb ok", "switch ok" -> "on" { }
    }
}
```

| Tick | Event | Branch 1 | Branch 2 |
|---|---|---|---|
| 2 | press | The split fires. Stack `test bulb` | Stack `test switch` |
| 3 | | ENTRY of `test bulb` runs, then `"test bulb" -> "bulb ok"` fires | `"test switch" -> "check position"` fires |
| 4 | | ENTRY of `bulb ok` runs | `"check position" -> "switch ok"` fires |
| 5 | | The join fires. Stack `on` | |
| 6 | | ENTRY of `on` runs | |

Since the join fires before the second branch enters `switch ok`, the ENTRY block of that state never runs to
set `mode` to `tested`.

A join sees the events of all branches but consumes its event for the new stack only.

Because a split into container states goes down into each of them, every branch starts inside its fragment. The rule
of [3.1.14.5 Final states and DONE](#31145-final-states-and-done) lets `DONE` on a join wait for all container
states among its sources.

In the trace log of [3.3.5 Trace log](3.3-running-the-runtime.md#335-trace-log) every branch has a path number of its
own. In the example the lamp runs on path 0 up to the split, branch 1 on path 1, branch 2 on path 2, and the stack
`on` after the join on path 3. A second split would start the paths 4 and 5. The lines of the two
branches can be told apart, also when they interleave with TrueParallel on, because every line of a branch names its
path.

## 3.1.9 Histories

With the feature History on, a state marked `SHALLOW HISTORY` or `DEEP HISTORY` remembers where it was. At the start of
each step the runtime looks at every active state with a history that has an active inner state and notes one of its
inner states.

- For `SHALLOW HISTORY` it notes the state right inside it.
- For `DEEP HISTORY` it notes the innermost active state.

When a transition later leads into the state itself, the state is entered. In the same tick the runtime then leads on
into the remembered state. The remembered state is entered only in the next tick, because this ends the step. A
container state with a history goes to the remembered state at once, without this extra tick, by the rules of
[3.1.14.6 Histories, tick limits and breakpoints](#31146-histories-tick-limits-and-breakpoints).

Each state machine instance has histories of its own. A history survives a stop and a start of the environment
but is forgotten when its instance leaves. Without the feature History the marks have no effect.

The state `on` of this lamp remembers whether it was `full` or `dimmed`.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        STATE "off" {
            ENTRY { SET("mode", "off") }
        }
        INITIAL SHALLOW HISTORY STATE "on" {
            ENTRY { SET("mode", "on") }
            STATE "full" {
                ENTRY { SET("bulb->watts", "40") }
            }
            STATE "dimmed" {
                ENTRY { SET("bulb->watts", "20") }
            }
        }
    }
    TRANSITIONS {
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
    }
}
```

| Tick | Event | lamp |
|---|---|---|
| 1 | | ENTRY of `on` and `full` run |
| 2 | dim | `"full" -> "dimmed"` fires |
| 3 | | ENTRY of `dimmed` runs |
| 4 | press | `"on" -> "off"` fires |
| 5 | | ENTRY of `off` runs |
| 6 | press | `"off" -> "on"` fires. Stack `on` |
| 7 | | ENTRY of `on` runs, then the history leads on to `dimmed` |
| 8 | | ENTRY of `dimmed` runs. `watts` is 20 |

## 3.1.10 Tick limits

With the feature TickLimit on, a `TICK LIMIT` block counts the ticks of its state, starting with the tick in which the
ENTRY block of the state runs. Each state machine instance counts its own ticks. A stop and a start of the environment
keep the counts. They are forgotten when the instance leaves. Without the feature TickLimit,
`TICK LIMIT` blocks have no effect.

`DELAY: n TICKS` holds the state for its first n ticks. A transition that would leave the state in that time does not
fire and keeps its event. No other transition fires in this step either.
`TIMEOUT: AFTER n TICKS TRANSITION TO "state"` leads to the named state in the tick after the first n ticks, after the
ENTRY blocks and before the DO block. A delay holds back a timeout as well. When several active states have a timeout
that is due, the timeout of the innermost one wins.

This lamp holds back the transition out of `off` for two ticks. In `on` its timeout leads back to `off` after three
ticks.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            TICK LIMIT { DELAY: 2 TICKS }
            ENTRY { SET("mode", "off") }
        }
        STATE "on" {
            TICK LIMIT { TIMEOUT: AFTER 3 TICKS TRANSITION TO "off" }
            ENTRY { SET("mode", "on") }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

| Tick | Event | lamp |
|---|---|---|
| 1 | | ENTRY of `off` runs. First tick of `off` |
| 2 | press | Second tick of `off`. The delay holds the transition, the press stays |
| 3 | | `"off" -> "on"` fires on the waiting press |
| 4 | | ENTRY of `on` runs. First tick of `on` |
| 5 | | Second tick of `on` |
| 6 | | Third tick of `on` |
| 7 | | The timeout leads to `off` |
| 8 | | ENTRY of `off` runs |
| 9 | press | Second tick of `off`. The delay holds the transition |
| 10 | | `"off" -> "on"` fires |

## 3.1.11 Forcing a state

The route `setActiveState` of the
[HTTP API](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/http-api.md#running)
puts a state machine into a named state while the environment runs. When the runtime applies it at the start of the
next tick, the stack becomes the path to the named state, with a single branch. No ENTRY block runs.

A state inside a container state is named with its qualified name, such as `self test/lit`. If the named state is a
container state, the runtime goes down into its fragment by the same rules of
[3.1.14.3 Entering a container state](#31143-entering-a-container-state) that hold for a transition.

The runtime drops every event of the domain whose name is the key of the object of the state machine. It also drops
every client event that has not reached the state machines yet, so that no event on its way can work against the
forced state.

The state machine that is forced is the instance that the object has in the latest tick, also when that instance
joined during the run. In the trace log the forced state ends the paths that the state machine ran and starts the
next path. The line `Forced state` names both.

## 3.1.12 Errors in a tick

An error in an action stops its block by the rule of [3.1.5.1 Blocks and errors](#3151-blocks-and-errors). An error
in an `EVAL` or `VALUE` clause makes the clause false. In all these cases the run goes on. The runtime writes the
error to its console and to the trace log, an error of an action as `ACTION_ERROR` and an error of a condition as
`CONDITION_ERROR`.

The errors that Python code gives are listed in [3.1.6.4 Errors in code](#3164-errors-in-code), together with the way
a call of Python code that does not end holds the ticks of the environment.

## 3.1.13 State machine management and lifecycle

An environment runs state machine instances. An instance is one state machine running on one object, with its own
stack and branches, its own events, histories and tick counts and its own overrides of breakpoints. Since an
object has at most one instance at a time, the key of the object names the instance. Attachable state machines,
`behaves after`, `ATTACH` and `EXCHANGE` are written as shown in
[2.3.11 State machine management and lifecycle](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2311-state-machine-management-and-lifecycle).

### 3.1.13.1 Where instances come from

An environment holds two kinds of state machines, both uploaded with the
[upload routes of the HTTP API](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/http-api.md#uploads).

- An attached state machine, `STATEMACHINE ATTACHED TO "Type"`, is uploaded with `attachedTo` and belongs to the
  object with that key.
- An attachable state machine, `STATEMACHINE "name" ATTACHABLE TO "Type", ...`, is uploaded without `attachedTo` and
  kept as a definition under its name.

An object gets an instance of a definition in four ways.

- Its type `behaves after` the definition, and the object is in the model when the environment starts.
- Its type `behaves after` the definition, and a rule creates the object.
- An `ATTACH` clause names the definition for the object that its rule creates.
- `EXCHANGE` gives the object the definition.

An attached state machine wins over the `behaves after` of the type of its object. In the same way an `ATTACH` clause
wins over the `behaves after` of the type of the object that the rule creates. Every new instance starts in its
initial state, found by the rule of [3.1.3.1 Initial state](#3131-initial-state).

`runEnvironment` makes sure that every object whose type behaves after a name can get its instance, also an object
that a rule creates later. It refuses an environment in which a type of the metamodel behaves after a name that no
attachable state machine has, or after a state machine that does not list the type, with the answer shown under
[Running](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/http-api.md#running)
in the description of the HTTP API.

### 3.1.13.2 The order of the steps

The instances step one after the other in a fixed order.

1. First come the attached state machines, in the order of their first upload.
2. Then come the instances for `behaves after` of the objects that are in the model at the start. They follow the
   order of the objects in the model, in which an object comes first and then the objects it holds, relation by
   relation, as the KModel text writes them.
3. Last come the instances that joined during the run, in the order in which they joined.

An instance that `EXCHANGE` gives an object takes the place of the instance it replaces. If the object had no instance
before, the new instance joins at the end.

### 3.1.13.3 When instances join and leave

The order changes only at the end of a tick, after every instance has done its step. A rule that creates objects asks
for the instances of the new objects, just as `EXCHANGE` asks for the new instance. These instances join at the end of
the tick. Each of them does its first step in the next tick, in which its ENTRY blocks run.

From the moment its object leaves the model or `EXCHANGE` replaces it, an instance has ended and does no further
step. If it stands later in the order, it skips its step in this tick. An instance can also end during its own
action block, when the block removes an object that holds its own object or exchanges its own state machine. It then
finishes the block, after which its step ends without looking for a transition. At the end of the tick the ended
instances leave the order. With each of them go its histories and tick counts and the overrides of breakpoints for
its object.

The same holds with the feature TrueParallel on, although the branches of a split then create, remove and exchange
objects at the same time on threads of their own. The requests of all branches are collected and carried out together
at the end of the tick. A request for an object that is no longer in the model at that point is dropped. With
TrueParallel on, an instance that ends during a step stops each of its branches after the block that the branch is
in.

### 3.1.13.4 New objects

`SETOBJ` and `APPENDOBJ` on a `has` relation create an object and every object it holds, from a dictionary of
[3.1.5.4 Objects and relations](#3154-objects-and-relations). A dictionary with the `__id__` of an existing object
creates in the same way the new objects that it lists in a `has` relation. Every new object whose type behaves after a
definition gets an instance of it. With `ATTACH name` after the rule, the object that the rule creates gets an
instance of `name` instead, while the objects it holds still follow their types.

The runtime reads the name of `ATTACH` before it computes the new object and checks the name against the type of the
relation. Since the name is read first, a name that is wrong in one of the ways of [3.1.13.7 Errors](#31137-errors)
fails the action before the rule has created anything.

### 3.1.13.5 EXCHANGE

`EXCHANGE("path", name)` ends the instance of the object at the path and gives the object an instance of `name`. The
path is read like the path of `DROPOBJ`. It starts at the object of the state machine and knows no keyword `self`.
Unlike for `DROPOBJ`, the object at the path may be the object of the state machine itself, reached over relations.
The instance then finishes its block and leaves, as described in
[3.1.13.3 When instances join and leave](#31133-when-instances-join-and-leave).

`EXCHANGE` with the name of the running definition starts the object again, in the initial state of a new instance.
If two `EXCHANGE` actions hit one object in one tick, the object keeps the instance of the second.

In the trace log an exchange is one line `STATE_MACHINE_EXCHANGED`. It names the object, the state machine that ended
and the one that started, the paths that ended and the path of the new instance. Two `EXCHANGE` on one object in one
tick give a single such line, from the state machine before the tick to the one named last. `EXCHANGE` on an object
without an instance gives the line `STATE_MACHINE_ATTACHED` instead. An instance that joins after another one has left
the same object goes on with the next path number of the object, for example after the object was removed and created
again with the same key. All these lines are explained in [3.3.5 Trace log](3.3-running-the-runtime.md#335-trace-log).

### 3.1.13.6 Removed objects

An object leaves the model in three ways, all of them described in
[3.1.5.4 Objects and relations](#3154-objects-and-relations).

- `DROPOBJ` removes it.
- A `SETOBJ` replaces it as the object of a `has` relation.
- A dictionary with the `__id__` of the object that holds it no longer lists it.

In every case the objects it holds leave with it and the instances of all these objects end. An instance that a rule
asked for in the same tick for one of these objects never joins. `DROPOBJ` cannot remove the object of its own state
machine, whatever path leads there, but it can remove an object that holds it.

### 3.1.13.7 Errors

The name of a state machine in `ATTACH` and `EXCHANGE` is given like any value of
[3.1.5.2 Values on the right side](#3152-values-on-the-right-side). A string is the name itself, while an `EVAL` or a
`MACRO` must return a string. The following are errors of the action, handled like the others of
[3.1.5.1 Blocks and errors](#3151-blocks-and-errors).

| Error | Text in the trace log |
|---|---|
| The value is not a string | `The name of a state machine must be a string, but the value is <value>` |
| No definition has the name | `No attachable state machine is named '<name>'` |
| The definition does not list the type of the object | `The state machine '<name>' is attachable to '<A>', '<B>', not to '<type>'` |
| `ATTACH` after a `knows` relation | `ATTACH needs a has relation, but '<relation>' is a knows relation; use EXCHANGE for an existing object` |
| The path of `EXCHANGE` leads to no object | `EXCHANGE path '<path>' does not resolve to an object` |

For `ATTACH` the type that is checked is the type of the relation, for `EXCHANGE` the type of the object at the path.
A failed `ATTACH` fails its whole rule. A failed `EXCHANGE` leaves the instance of the object as it was.

### 3.1.13.8 Example

The example runs on the metamodel of
[2.3.11 State machine management and lifecycle](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2311-state-machine-management-and-lifecycle),
in which `Bulb` behaves after `glowing` and `Room` has spare bulbs. The model holds the room `living room` with the
lamp `lamp`, the bulb `bulb` of the lamp with `maxWatts` 40 and `watts` 0, and the switch `wallSwitch`. The
environment holds the attachable state machines `glowing` and `blinking` of 2.3.11. The following state machine of
the room, also taken from 2.3.11, is attached to `living room`.

```kstates
STATEMACHINE ATTACHED TO "Room" {
    STATES {
        INITIAL STATE "waiting" { }
        STATE "stocked" {
            ENTRY {
                APPENDOBJ("self", "spares", MACRO("new bulb", "lamp->bulb->maxWatts")) ATTACH "blinking"
            }
        }
        STATE "party" {
            ENTRY {
                EXCHANGE("lamp->bulb", "blinking")
            }
        }
    }
    TRANSITIONS {
        TRANSITION "waiting" -> "stocked" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "stocked" -> "party" {
            CONDITION { EVENT("switch", "press") }
        }
    }
    MACROS {
        MACRO "new bulb" {
            TAKES("watts", "number")
            RETURNS("Bulb")
            DEFINITION {
                EVAL { return {"maxWatts": $(watts), "watts": $(watts)} }
            }
        }
    }
}
```

At the start the room gets its attached state machine and `bulb` an instance of `glowing`, in this order. In the run
below a press came before tick 3 and another before tick 6. The spare bulb that the room creates got the key
`gen_Bulb_0`.

| Tick | Event | living room | bulb | gen_Bulb_0 |
|---|---|---|---|---|
| 1 | | Stack `waiting` | ENTRY of `dark` of `glowing` runs. Since `watts` is 0, the bulb stays in `dark` | |
| 3 | press | `"waiting" -> "stocked"` fires | Stack `dark` | |
| 4 | | ENTRY of `stocked` creates `gen_Bulb_0` with `ATTACH "blinking"` | Stack `dark` | Joins at the end of the tick, after `bulb` |
| 5 | | Stack `stocked` | Stack `dark` | ENTRY of `off` runs, then `"off" -> "on"` fires |
| 6 | press | `"stocked" -> "party"` fires | Stack `dark` | ENTRY of `on` runs, then `"on" -> "off"` fires |
| 7 | | ENTRY of `party` exchanges the state machine of `bulb` | No step. It leaves at the end of the tick. An instance of `blinking` takes its place | ENTRY of `off` runs |
| 8 | | Stack `party` | ENTRY of `off` of `blinking` runs, then `"off" -> "on"` fires | ENTRY of `on` runs |

In tick 8 the order is `living room`, `bulb`, `gen_Bulb_0`, because the new instance of `bulb` took the place of the
old one. The trace log shows the change of tick 7 as one line for `bulb`,
`STATE_MACHINE_EXCHANGED: State machine 'glowing' exchanged for 'blinking'`, with `ends=0, path=1`. A
`DROPOBJ("lamp")` in the room would end the instance of `bulb` in the same way, because the lamp holds the bulb, but
nothing would take its place.

### 3.1.13.9 Stop and start, forcing and clients

Only the first start builds instances over the model. Because a stop freezes the environment, a start after it can
go on with the next tick as if there had been no stop. The stop leaves all of the following as it found it.

- every instance, also those that `ATTACH` and `EXCHANGE` gave objects, with its place in the order
- the stacks and branches of every instance, the events it consumed and its scoped events
- the histories, the counts of tick limits, and the state and overrides of breakpoints
- the number of the tick, and with it the lists of EventRecording and EventInjection
- the path numbers of the trace log, with which the branches go on with their paths and new paths count on
- the pause of TickByTick and a halt at a breakpoint
- the events on the bus with the time to live they had left at the stop, because the time while the environment is
  stopped does not count

A stopped environment stays frozen in the runtime until it is started again, until `POST /dropEnvironment` of the
[HTTP API](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/http-api.md#environments)
drops it or until the runtime ends. A drop ends it for good, also when the environment was stopped while a
breakpoint halted it.

Nothing that ran before the stop runs again: no ENTRY block runs twice and no instance starts anew. A stop lets the
running tick end first. If the run waits at a breakpoint inside a tick, though, the halted tick stays as it is until
the start and a `resume`. Events that clients send while the environment is stopped wait and reach the state machines
after the start.

`setActiveState` of [3.1.11 Forcing a state](#3111-forcing-a-state) works on the instance that an object has in the
latest tick, also on one that joined during the run.

Clients learn about instances through the member `stateMachines` of the model snapshot and through the messages
`stateMachineAttached` and `stateMachineDetached` of the
[WebSocket of the runtime](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/websocket.md#statemachineattached-and-statemachinedetached).
Both messages name the object and the definition. At the first start every instance is reported before the first
tick, while a start after a stop reports nothing anew. An instance that joins is reported at the end of the tick in
which it joined. Its first stack follows after its first step. When an instance leaves, this is reported at the end
of the tick in which it ended. From then on its stack is missing from the snapshot.

## 3.1.14 Pages

Container states, fragments, final states and the clause `DONE` split a state machine into pages. They belong to the
core language and need no feature to be switched on. How they are written is the subject of
[2.3.12 Pages](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2312-pages).

### 3.1.14.1 Flattening at activation

Before anything runs, `runEnvironment` flattens every attached and every attachable state machine of the environment
with the fragments of the environment. In the flat state machine a container state holds a copy of the states of its
fragment as its inner states. A fragment that two container states use runs as two copies that share nothing. The
engine runs only these flat state machines.

If a state machine does not flatten, for example because one of its container states uses a fragment that the
environment does not hold, `runEnvironment` refuses to activate the environment with the answer shown under
[Running](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/http-api.md#running)
in the description of the HTTP API. The environment then stays configurable for the missing upload and another
`runEnvironment`.

An attachable state machine is flattened once. Every instance of it runs the same flat state machine, whether the
instance comes from `behaves after`, `ATTACH` or `EXCHANGE`. The environment keeps the texts as they were uploaded.
These texts, unflattened, are what `observatory/statemachine` answers with.

### 3.1.14.2 Qualified names

A state of a fragment runs under a qualified name made of the name of its container state, a slash and its name in
the fragment. The state `lit` of the fragment `bulb test` below runs as `self test/lit`. When a fragment uses another
fragment, the names nest, for example to `self test/wiring/lit`. A state that stands inside another state of the
fragment gets only the container state in front of its name: `high` inside `second` runs as `self test/high`. The
states of the state machine itself keep their names.

These names are used in the trace log, in the message `stateChange`, in the member `activeStates` of the snapshot and
by `setActiveState`. In a state machine without container states every state keeps its plain name.

### 3.1.14.3 Entering a container state

Whenever a container state is entered, the runtime goes down into it at once. The stack then reaches into the states
that the fragment starts in, chosen by the rule of [3.1.3.1 Initial state](#3131-initial-state), and further down as
long as one of them is a container state again. This holds for every way of entering a state.

- the start of an instance, also of the instances that `behaves after`, `ATTACH` and `EXCHANGE` start
- a transition
- a split
- a join
- the timeout of a tick limit
- a history
- `setActiveState`

A stack therefore never ends on a container state. A state with inner states written in its braces is different,
because a transition enters it as itself by the rule of
[3.1.4.3 Where a transition leads](#3143-where-a-transition-leads).

Like the other states that a transition enters, the states below the container state are entered in the next tick,
from the outside in. A container state itself has no ENTRY and no DO block.

The examples below use the fragment `bulb test`. It lights the bulb, darkens it on a `dim` and reaches its final
state `passed` on a second `dim`.

```kstates
STATEMACHINE "bulb test" FRAGMENT {
    STATES {
        INITIAL STATE "lit" {
            ENTRY { SET("bulb->lit", "true") }
        }
        STATE "dark" {
            ENTRY { SET("bulb->lit", "false") }
        }
        FINAL STATE "passed" { }
    }
    TRANSITIONS {
        TRANSITION "lit" -> "dark" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "dark" -> "passed" {
            CONDITION { EVENT("switch", "dim") }
        }
    }
}
```

The lamp runs the fragment in its container state `self test`.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            ENTRY { SET("mode", "off") }
        }
        CONTAINER STATE "self test" USE "bulb test" { }
        STATE "on" {
            ENTRY { SET("mode", "on") }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "self test" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "self test" -> "on" {
            CONDITION { DONE }
        }
        TRANSITION "self test" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

In this run a press came before tick 2 and a `dim` before tick 4 and again before tick 6.

| Tick | Event | lamp |
|---|---|---|
| 1 | | ENTRY of `off` runs. Stack `off` |
| 2 | press | `"off" -> "self test"` fires. Stack `self test`, `self test/lit` |
| 3 | | ENTRY of `self test/lit` runs. `lit` is true |
| 4 | dim | `"self test/lit" -> "self test/dark"` fires |
| 5 | | ENTRY of `self test/dark` runs. `lit` is false |
| 6 | dim | `"self test/dark" -> "self test/passed"` fires. Stack `self test`, `self test/passed` |
| 7 | | `DONE` holds and `"self test" -> "on"` fires. Stack `on` |
| 8 | | ENTRY of `on` runs |

### 3.1.14.4 Leaving a container state

Because the container state is active around the states of its fragment, its transitions apply in every one of them,
as those of any outer state do. A transition that leaves the container state drops all its inner states. A
press during the self test above leads back to `off` from `self test/lit` as well as from `self test/dark`. Once the
lamp has reached `self test/passed` in tick 6 of the table, it goes on to `on` in tick 7 even if a press arrives,
because the transition with `DONE` is written before the one on the press and fires first. After a return to `off`,
the next press starts the fragment again in `self test/lit`.

Since the runtime looks for transitions from the innermost state outwards, a transition of a state of the fragment
wins over one of the container state when both could fire.

### 3.1.14.5 Final states and DONE

A final state has no actions and no transitions of its own. The stack rests on it while the runtime goes on trying the
transitions of the states around it, as for every state. As long as none of them leads out of the container state,
the stack stays on the final state.

On a `TRANSITION` or a `SPLIT`, `DONE` holds exactly while the state right inside the container state that the
transition leaves is a final state of its fragment. If the condition has other clauses, all of them must hold as well.
An event that such a condition waits for is treated as for any condition whose other clauses do not hold. When
nothing fires in the step, the event is consumed in the second way of [3.1.7.3 Consumption](#3173-consumption). With
`CONDITION { EVENT("switch", "abort") DONE }`, an `abort` that arrives before the fragment rests on a final state is
lost in this way. Only an `abort` that comes after that leads out. On a `JOIN`, by contrast, the event waits until
`DONE` holds, as long as its time to live is not over.

`DONE` holds again each time the fragment rests on a final state, also after the container state was left and entered
again and its fragment ran to its end once more.

Leaving through a final state takes one step more than a transition that leads straight out, because the transition
into the final state ends its step and `DONE` can fire in the next tick at the earliest. In the example of
[3.1.14.3 Entering a container state](#31143-entering-a-container-state) the lamp reaches `self test/passed` in tick
6 and leaves `self test` in tick 7.

On a `JOIN`, `DONE` holds when each source of the join that is a container state rests on a final state in the branch
that stands in it. Sources that are not container states do not count for `DONE`, but the join still needs one branch
per source, like every join of [3.1.8 Splits and joins](#318-splits-and-joins). In the second lamp of
[2.3.12.2 Container states and DONE](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#23122-container-states-and-done),
the split starts one branch in `bulb check/powered` and one in `switch check/waiting`. A branch that reaches a final
state rests there until the other one has reached one as well, at which point the join fires. The join works in the
same way when the feature TrueParallel lets the branches run on threads of their own.

### 3.1.14.6 Histories, tick limits and breakpoints

With the feature History on, a container state with a history remembers like any other state, `SHALLOW HISTORY` the
state right inside it and `DEEP HISTORY` the innermost active state. When the container state is entered again, the
runtime goes to the remembered state at once, in the same step, in place of starting the fragment. A state with inner
states written in its braces behaves differently, since it first rests on itself for one tick before its history
leads on. In the example of [3.1.9 Histories](#319-histories) the stack is `on` alone after tick 6. The history
leads on only in tick 7.

A remembered state with inner states of its own is entered as itself, as by a transition, while the runtime goes down
into a remembered container state. Without something to remember, or without the feature History, the fragment
starts as usual.

A `TICK LIMIT` of a container state counts the ticks of the container state while any state of its fragment is active.
Its delay holds back only the transitions that leave the container state, while the transitions inside the fragment
fire as usual. Its timeout leads out of the container state. A timeout that leads into a container state goes down
into it.

A `BREAKPOINT` on the entry of a container state halts the run before the container state and the
states of its fragment below it are entered. Breakpoints of the states of a fragment work as on any other state. Since
each copy of a fragment has its own states, a breakpoint in one copy halts only that copy.

### 3.1.14.7 The trace log

The lines of the trace log of [3.3.5 Trace log](3.3-running-the-runtime.md#335-trace-log) name the states by their
qualified names. In the example of [3.1.14.3 Entering a container state](#31143-entering-a-container-state), tick 4
writes the line `TRANSITION_FIRED: self test/lit -> self test/dark` with `from=self test/lit, to=self test/dark` and
`stack=self test,self test/dark`. An instance that starts in a container state writes
`Initial state stack: self test > self test/lit`. A `setActiveState` with `self test` writes
`Forced state: self test > self test/lit`.

### 3.1.14.8 Compound states and container states

A compound state holds inner states written in its braces, a container state the copy of a fragment.
[2.3.13 Compound states and container states](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2313-compound-states-and-container-states)
compares what each of them can be written with, their names and their macros. At run time they differ in these
points.

| Point | Compound state | Container state |
|---|---|---|
| A transition into the state itself | Enters the state alone and rests on it. Its inner states are not entered | Enters the state and the start of its fragment in the same step. The stack never ends on the container state |
| A transition into an inner state | Enters the compound state too, when it was not active | Not possible: no file names a state of a fragment it uses |
| ENTRY and DO | The compound state has its own blocks. Its DO runs while it is the innermost state | The container state has none |
| Names in the trace log and in `stateChange` | The names as written: `self test`, `lit` | Qualified: `self test`, `self test/lit` |
| Re-entry with a history | Rests on itself for one tick, then leads on to the remembered state | Goes to the remembered state at once |
| End of the inner behaviour | A transition of an inner state leads out | The fragment rests on a final state, and `DONE` on a transition of the container state leads out |
| A transition of the outer state | Leaves every inner state | Leaves every state of the fragment |

The same self test can be written both ways. With a compound state the transitions lead into its inner states.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "self test" {
            STATE "lit" {
                ENTRY { SET("bulb->lit", "true") }
            }
            STATE "dark" {
                ENTRY { SET("bulb->lit", "false") }
            }
            STATE "passed" { }
        }
        STATE "on" {
            ENTRY { SET("mode", "on") }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "lit" { }
        TRANSITION "lit" -> "dark" { }
        TRANSITION "dark" -> "passed" { }
        TRANSITION "passed" -> "on" { }
    }
}
```

With a container state the fragment holds the steps and `DONE` leads out.

```kstates
STATEMACHINE "bulb test" FRAGMENT {
    STATES {
        INITIAL STATE "lit" {
            ENTRY { SET("bulb->lit", "true") }
        }
        STATE "dark" {
            ENTRY { SET("bulb->lit", "false") }
        }
        FINAL STATE "passed" { }
    }
    TRANSITIONS {
        TRANSITION "lit" -> "dark" { }
        TRANSITION "dark" -> "passed" { }
    }
}
```

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        CONTAINER STATE "self test" USE "bulb test" { }
        STATE "on" {
            ENTRY { SET("mode", "on") }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "self test" { }
        TRANSITION "self test" -> "on" {
            CONDITION { DONE }
        }
    }
}
```

Both forms run in the same ticks and differ only in the names. Since an ENTRY block with actions is followed at once
by the search for a transition, `lit` and `dark` are left in the tick in which they are entered.

| Tick | Compound state | Container state |
|---|---|---|
| 1 | `"off" -> "lit"` fires. Stack `self test`, `lit` | `"off" -> "self test"` fires. Stack `self test`, `self test/lit` |
| 2 | ENTRY of `lit` runs, then `"lit" -> "dark"` fires | ENTRY of `self test/lit` runs, then `"self test/lit" -> "self test/dark"` fires |
| 3 | ENTRY of `dark` runs, then `"dark" -> "passed"` fires. Stack `self test`, `passed` | ENTRY of `self test/dark` runs, then `"self test/dark" -> "self test/passed"` fires. Stack `self test`, `self test/passed` |
| 4 | `"passed" -> "on"` fires. Stack `on` | `DONE` holds and `"self test" -> "on"` fires. Stack `on` |
| 5 | ENTRY of `on` runs | ENTRY of `on` runs |

If the first text had `TRANSITION "off" -> "self test" { }`, the compound state would be entered alone. The stack
would stay `self test`. Since no inner state would ever be entered, `bulb->lit` would never change. A container state
cannot be entered in that way, because entering it always starts its fragment.

## 3.1.15 Where the engine goes

This section gathers in one place where a stack goes when states are entered, which states are entered and in which
tick their ENTRY blocks run. The rules behind it are those of [3.1.3 Active states](#313-active-states),
[3.1.4 Transitions](#314-transitions) and [3.1.14 Pages](#3114-pages).

### 3.1.15.1 Ways of entering

A step of a state machine ends with the first transition that fires. The states that a transition enters run their
ENTRY blocks from the outside in during the next step of the same branch, that is in the next tick. An ENTRY block
with at least one action is followed by a search for a transition. If one fires, the ENTRY blocks further inside do
not run.

| Way | When the stack changes | ENTRY of the entered states |
|---|---|---|
| Start of the environment | Before tick 1. The stack is the start path of [3.1.3.1 Initial state](#3131-initial-state) | Tick 1, every state of the start path |
| Instance that joins during the run (`behaves after` of a created object, `ATTACH`, `EXCHANGE`) | At the end of the tick that asked for it. The stack is the start path of its state machine | The next tick, its first step |
| Transition | In the step that fires it | The next tick |
| Split | In the step that fires it. One stack per target | The next tick, in each branch |
| Join | At the start of the step, before every other transition. One stack | The next tick |
| Timeout of a tick limit | In the step, after the ENTRY blocks and before the DO block, which then does not run | The next tick |
| History of a compound state | In the step after the compound state was entered, right after its ENTRY block. Its DO block does not run | The tick after that |
| History of a container state | In the same step as the transition into the container state | The next tick |
| `setActiveState` | At the start of the next tick, before any step | Never. The forced states count as entered without running their ENTRY blocks, and the step of that tick goes on with the DO block of the innermost one |

A transition can follow right after the ENTRY blocks of a newly joined instance in its first tick, because that tick
looks for transitions as every other step does.

### 3.1.15.2 Kinds of target

| Target | Stack afterwards | Entered | The branch rests on |
|---|---|---|---|
| A state without inner states | The path from the top level to the state | The states of the path that were not active | The state |
| A compound state | The path to the compound state, nothing below it | The states of the path that were not active | The compound state. Its DO block runs from the next tick. With a history that remembers a state, it leads on one tick later |
| An inner state of a compound state | The path to the inner state | The compound state too, when it was not active | The inner state |
| A container state | The path to the container state and the start path of its fragment, or the remembered state of its history | The container state, when it was not active, and every state below it | The innermost state of the fragment, never the container state alone |
| A state of a fragment, by a transition of the fragment | The path to the state, inside the container state | The states of the path that were not active. The container state stays active and is not entered again | The state |
| A final state | The path to the final state | The final state | The final state, until a transition of a state around it fires |

By the rule of [3.1.4.3 Where a transition leads](#3143-where-a-transition-leads), a transition from a state to
itself, or to one of the states around it, enters the target again together with the state around it. For a
container state this means that `"self test" -> "self test"` leaves the fragment, enters `self test` again and starts
its fragment anew.

### 3.1.15.3 The start and the INITIAL mark

The start follows the `INITIAL` mark through every compound state, wherever the mark stands, by the rule of
[2.3.2.2 The initial state](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#2322-the-initial-state).
For the following lamp the stack at the start is `on`, `dimmed`, although `off` is the first state of the top level.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        STATE "off" { }
        STATE "on" {
            STATE "full" { }
            INITIAL STATE "dimmed" { }
        }
    }
    TRANSITIONS { }
}
```

Both states of the start stack are entered in tick 1.

The mark of a fragment is not seen from the state machine that uses it. Since a container state never counts as
holding a mark, the start does not choose it because of the mark inside its fragment. In the following lamp the fragment
`levels` marks its state `dimmed`, yet the start is `spare`, `ready`.

```kstates
STATEMACHINE "levels" FRAGMENT {
    STATES {
        STATE "full" { }
        INITIAL STATE "dimmed" { }
        FINAL STATE "out" { }
    }
    TRANSITIONS { }
}
```

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        STATE "off" { }
        CONTAINER STATE "on" USE "levels" { }
        STATE "spare" {
            INITIAL STATE "ready" { }
        }
    }
    TRANSITIONS { }
}
```

Since a state machine must mark one of its own states, `on` is the start only when it carries the mark itself, in
`INITIAL CONTAINER STATE "on" USE "levels"`. The start is then `on`, `on/dimmed`, because inside the container state
the mark of its fragment counts. A text without any mark of its own is refused at the upload with
`kstates.initial-state-count`.

### 3.1.15.4 Entering and leaving, tick by tick

The following lamp has a transition into a compound state and one into a state inside it.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            ENTRY { SET("mode", "on") }
            STATE "full" { }
            STATE "dimmed" { }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

This lamp got a press before tick 2, a press before tick 4 and a `dim` before tick 6.

| Tick | Event | lamp |
|---|---|---|
| 2 | press | `"off" -> "on"` fires. Stack `on` |
| 3 | | ENTRY of `on` runs. Stack `on`. `full` and `dimmed` are not entered |
| 4 | press | `"on" -> "off"` fires. Stack `off` |
| 6 | dim | `"off" -> "dimmed"` fires. Stack `on`, `dimmed` |
| 7 | | ENTRY of `on` runs, then the stack rests on `dimmed` |

With a history the compound state leads on one tick later. For the next run the text above has
`SHALLOW HISTORY STATE "on"` and the feature History is on. After a press has left the stack `on`, `dimmed`, another
press leads back into `on`.

| Tick | Event | lamp |
|---|---|---|
| k | press | `"off" -> "on"` fires. Stack `on` |
| k+1 | | ENTRY of `on` runs, then the history leads on. Stack `on`, `dimmed` |
| k+2 | | ENTRY of `dimmed` runs |

A container state with a history reaches the remembered state in tick k already. In the next run the lamp of
[3.1.14.3 Entering a container state](#31143-entering-a-container-state) has
`SHALLOW HISTORY CONTAINER STATE "self test" USE "bulb test"`. A press leaves `self test` while the lamp is in
`self test/dark`. The next press leads back into it.

| Tick | Event | lamp |
|---|---|---|
| k | press | `"off" -> "self test"` fires. Stack `self test`, `self test/dark` |
| k+1 | | ENTRY of `self test/dark` runs |

Without the feature History, or while the history remembers nothing yet, the stack in tick k is `self test`,
`self test/lit`.

A transition that leaves a state leaves every state inside it as well, whatever is active there. Nothing runs
for the states that are left, because states have no exit blocks. The stack becomes the path to the target. The target
is entered as the tables above show. A transition of an inner state wins over one of the state around it when both could
fire, because the runtime looks from the innermost state outwards.

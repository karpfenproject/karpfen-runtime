# 3.2 Runtime features

A feature is a part of the runtime that a client switches on for one environment. In a new environment all features
are off. Two of them, History and TickLimit, give constructs of the language their effect at run time: History the
marks `SHALLOW HISTORY` and `DEEP HISTORY`, TickLimit the `TICK LIMIT` blocks. TrueParallel runs the branches of a
split on threads of their own. With the remaining features a client steps through a run, halts it at breakpoints, or
records the events of a run to replay them later.

| Feature | What it does | Needs |
|---|---|---|
| `History` | Gives the history marks of states their effect | |
| `TickLimit` | Gives `TICK LIMIT` blocks their effect | |
| `TickByTick` | Pauses the run and advances it tick by tick | |
| `Breakpoint` | Halts the run at the entry and exit of states and at the start and end of transitions | `TickByTick` |
| `EventRecording` | Records the events that clients send, by tick | |
| `EventInjection` | Hands a list of events to the state machines at given ticks | |
| `EventReplayController` | Turns a recording into the list of EventInjection | `EventRecording`, `EventInjection` |
| `TrueParallel` | Lets the branches of a split do their steps at the same time, each on a thread of its own | |

## 3.2.1 Switching features

The routes for features are listed in [3.4.10 Features](3.4-http-api.md#3410-features). A client switches a feature
on with `activateFeature` and off with `deactivateFeature`, in any phase of the environment. A switch takes effect at
once, also in the middle of a run. Only TrueParallel waits for the start of the next tick.

Switching a feature on also switches on the features it needs. Switching a feature off also switches off the features
that need it, together with the features that were only switched on because it needed them. Switching off
`TickByTick`, for example, switches off `Breakpoint`.

A client talks to a feature with `sendMessageToFeature`. The message is the body of the request, as text. The body of
the answer holds what the feature answers. History, TickLimit and TrueParallel take no messages and answer
every message with an empty body. The messages of the other features are given in their sections below.

Here a client switches TickByTick on and asks it for its status.

```bash
curl -X POST "http://127.0.0.1:8080/activateFeature?envKey=env-1763035112345&featureName=TickByTick"
curl -X POST "http://127.0.0.1:8080/sendMessageToFeature?envKey=env-1763035112345&featureName=TickByTick" -d "status"
```

```text
running
```

## 3.2.2 History

With History on, a state marked `SHALLOW HISTORY` or `DEEP HISTORY` that is entered again leads on into the inner
state it was in before. [3.1.9 Histories](3.1-execution-semantics.md#319-histories) gives the rules with an example.
What holds for a container state is added in
[3.1.14.6 Histories, tick limits and breakpoints](3.1-execution-semantics.md#31146-histories-tick-limits-and-breakpoints).
A stop and a start of the environment keep what a state remembers. Switching History off forgets it.

## 3.2.3 TickLimit

With TickLimit on, `DELAY` holds a state for its first ticks and `TIMEOUT` leaves a state after a number of ticks.
[3.1.10 Tick limits](3.1-execution-semantics.md#3110-tick-limits) has the rules and an example. A stop and a start of
the environment keep the counts.

## 3.2.4 TickByTick

TickByTick pauses the run between two ticks and lets it advance by a given number of ticks. A paused environment
still takes events from clients and answers requests for snapshots of its model.

| Message | Answer | What happens |
|---|---|---|
| `pause` | `execution paused` | The run waits before its next tick |
| `resume` | `execution resumed` | The run goes on |
| `tick:N` | `execution is advancing N tick(s)` | The paused run does N more ticks and waits again. The answer says `tick` for 1 and `ticks` for more |
| `status` | `paused` or `running` | |

`tick:N` works only while the run is paused and no earlier `tick:N` is still under way. Otherwise the answer is
`execution is currently not paused, ticks will not be applied`. With N less than 1 the answer is
`amount of ticks must not be less than one`. Any other message is refused with status 400 and the text
`Invalid message: <message>`.

A client that wants to step from the first ticks on sends `pause` after the start, because the first start of an
environment resumes a paused run. Switching TickByTick off resumes the run as well. A stop keeps the pause: after the
next start the run still waits. A `resume` or `tick:N` sent while the environment is stopped takes effect only
after the start.

While TickByTick is on, every client connected to the environment over the WebSocket gets the message
`engineStatus` each time the run starts to wait and each time it goes on.
[3.5.3.5 engineStatus](3.5-websocket.md#3535-enginestatus) shows what the message holds.

Two messages pause the run and let it do three more ticks.

```bash
curl -X POST "http://127.0.0.1:8080/sendMessageToFeature?envKey=env-1763035112345&featureName=TickByTick" -d "pause"
curl -X POST "http://127.0.0.1:8080/sendMessageToFeature?envKey=env-1763035112345&featureName=TickByTick" -d "tick:3"
```

```text
execution paused
execution is advancing 3 ticks
```

## 3.2.5 Breakpoint

Breakpoint halts the run at a place inside a tick. Because the run then waits in the same way as when TickByTick has
paused it, two messages to TickByTick end the wait. `resume` continues the run. `tick:1` takes it on to the next
breakpoint or to the start of the next tick, whichever comes first.

### 3.2.5.1 Places

| Place | When |
|---|---|
| Entry of a state | Before the ENTRY block of the state runs, also when the block is empty |
| Exit of a state | When a transition leaves the state, before the transition starts. The states left are taken from the innermost outwards. A transition from a state to itself leaves no state |
| Start of a transition | Before the transition changes the active states |
| End of a transition | After the transition changed the active states |

A transition that a `DELAY` holds back halts nowhere. The timeout of a `TICK LIMIT` and the step into the state that a
history remembers count as transitions, but since they have no text in which a breakpoint could be marked, only an
override halts at their start or end.

### 3.2.5.2 Breakpoints in the text and overrides

A state machine marks breakpoints in its text with `BREAKPOINT { ENTRY EXIT }` in a state and
`BREAKPOINT { START END }` in a transition, in the syntax of
[2.3.9 Breakpoints](https://github.com/karpfenproject/karpfen-dsl-tools/blob/main/docs/reference/2.3-kstates.md#239-breakpoints).
An override switches a breakpoint on or off at run time, whatever the text says. Overrides belong to the environment
and stay when it is started again. The overrides of an object are dropped when its state machine instance leaves, in
any of the ways of
[3.1.13 State machine management and lifecycle](3.1-execution-semantics.md#3113-state-machine-management-and-lifecycle).
An instance that later runs on the object starts with the breakpoints of its own text.

Every message to Breakpoint is a JSON object whose entry `action` says what to do. The further entries depend on the
action.

| Action | Further entries | Answer |
|---|---|---|
| `addStateOverride` | `modelElementId`, `stateIdentifier`, `timing` (`entry` or `exit`), `breakpointStatus` (`true` or `false`) | `Breakpoint override has added a breakpoint on state <state> entry in statemachine attached to <object>`, with `removed` for `false` and `exit` for the exit |
| `removeStateOverride` | `modelElementId`, `stateIdentifier`, `timing` | `Breakpoint override on state <state> entry has been removed in statemachine attached to <object>` |
| `addTransitionOverride` | `modelElementId`, `transitionIdentifier`, `timing` (`start` or `end`), `breakpointStatus` | `Breakpoint override has added a breakpoint on transition <transition> start in statemachine attached to <object>` |
| `removeTransitionOverride` | `modelElementId`, `transitionIdentifier`, `timing` | `Breakpoint override on transition <transition> start has been removed in statemachine attached to <object>` |
| `getOverrides` | | The overrides in four groups, as shown below |
| `getStatus` | | The status of the run as JSON, as shown below |

`modelElementId` is the key of the object the state machine instance runs on. `stateIdentifier` is the name of the
state. A message the feature cannot carry out gets one of the following answers, all of them with status 200.

| Case | Answer |
|---|---|
| A wrong timing | Starts with `Breakpoint override could not be added` or `Breakpoint override could not be removed` |
| An unknown action | `Invalid action: <action>` |
| A message that is no JSON or lacks an entry | Starts with `Error when parsing the message:` |

`transitionIdentifier` names the transition in the form in which the runtime writes it. For
`TRANSITION "off" -> "full"` with an `EVENT` clause the identifier is this text.

```text
Transition(fromState=off, toState=full, allowLoops=true, startBreakpoint=false, endBreakpoint=false, condition=EVENT)
```

| Part | Value |
|---|---|
| `allowLoops` | `false` for a transition marked `NOT LOOPING` |
| `startBreakpoint`, `endBreakpoint` | Whether the text marks the breakpoint at the start and at the end |
| `condition` | `VALUE` for a transition without `CONDITION`. `EVENT`, `EVAL` or `VALUE` for a condition of one clause, and `COMPOSITE` for a condition of more clauses |

The identifier of a split begins with `SplitTransition(fromState=off, toStates=[test bulb, test switch], ...` and the
one of a join with `JoinTransition(fromStates=[bulb ok, switch ok], toState=on, ...`. Transitions with the same
identifier share their overrides. The entry `halt` of the status in 3.2.5.3 names a transition in the same form.

This message switches on a breakpoint at the entry of the state `on` of the lamp.

```json
{
  "action": "addStateOverride",
  "modelElementId": "lamp",
  "stateIdentifier": "on",
  "timing": "entry",
  "breakpointStatus": true
}
```

```text
Breakpoint override has added a breakpoint on state on entry in statemachine attached to lamp
```

After this message `getOverrides` lists the one override in the group of the entry breakpoints.

```text
{Entry Breakpoints={lamp={on=true}}, Exit Breakpoints={}, Start Breakpoints={}, End Breakpoints={}}
```

### 3.2.5.3 Status

`getStatus` answers with a JSON object. The WebSocket message `engineStatus` carries the same object as its payload.

| Entry | Meaning |
|---|---|
| `paused` | `true` from the moment a pause is asked for until the run is resumed |
| `waiting` | `true` while the run waits |
| `halt` | There only while the run waits at a breakpoint. It names the place |

At a state, `halt` names the object, the timing, `entry` or `exit`, and the state. This is a halt at the entry of
`on`.

```json
{"paused":true,"waiting":true,"halt":{"modelElementId":"lamp","timing":"entry","state":"on"}}
```

At a transition, `halt` names the transition by its identifier and has four more entries.

| Entry | Meaning |
|---|---|
| `kind` | `TRANSITION`, `SPLIT` or `JOIN` |
| `from`, `to` | The source states and the target states |
| `index` | The place of the transition in the `TRANSITIONS` block of its file, counted from 0. A timeout and the step into a remembered state have the index -1 |

A halt at the start of the transition from `off` to `full` gives this status.

```json
{"paused":true,"waiting":true,"halt":{"modelElementId":"lamp","timing":"start","transition":"Transition(fromState=off, toState=full, allowLoops=true, startBreakpoint=false, endBreakpoint=false, condition=EVENT)","kind":"TRANSITION","from":["off"],"to":["full"],"index":0}}
```

The order of the entries in these objects is not fixed.

## 3.2.6 EventRecording

EventRecording records the events that clients send over the WebSocket, each under the number of the tick in which it
reaches the state machines. While the feature records, an event from a client waits for the start of the next tick
before it reaches them. Events that the state machines raise and injected events are not recorded.

| Message | Answer | What happens |
|---|---|---|
| `start` | `recording started` | Recording starts |
| `stop` | `recording stopped` | Recording stops. Events that wait for the next tick go to the state machines at once |
| `get` | The recording as JSON | |
| `clear` | `cleared recorded events` | The recording is emptied |

Any other message gets the answer `invalid message: <message>`. A recording stays when the environment is stopped and
started again. Because the ticks then go on with the next number, the recording continues where it stopped.

The recording is a JSON object whose keys are tick numbers. The value of a key is the list of the events of that tick.
In the list each event is a string that holds a JSON object.

```json
{"5": ["{\"environmentKey\":\"switch\",\"messageType\":\"dim\",\"payload\":\"{\\\"bright\\\": false}\",\"payloadFormat\":\"JSON\"}"]}
```

| Entry | Meaning |
|---|---|
| `environmentKey` | The domain of the event |
| `messageType` | The name of the event |
| `payload` | The payload as text |
| `payloadFormat` | `NONE`, `JSON` or `KMODEL` |

The order of the entries is not fixed.

## 3.2.7 EventInjection

EventInjection holds a list of events by tick and hands each event to the state machines at the start of its tick.

| Message | Answer | What happens |
|---|---|---|
| `upload:<list>` | `successfully uploaded events` | Replaces the list |
| `start` | `injection started` | Injection starts |
| `stop` | `injection stopped` | Injection stops |
| `get` | The list as JSON | |
| `clear` | `cleared event queue` | The list is emptied |

Any other message gets the answer `invalid message: <message>`.

The list behind `upload:` has the form of a recording. An event in it may be a string that holds a JSON object, as in
a recording, or the JSON object itself. Every event needs `environmentKey`, `messageType` and `payload`, while
`payloadFormat` may be left out. A list that cannot be read is refused with an error status and the reason as
text. The list uploaded before stays in place.

While injection runs, the runtime takes at the start of each tick every event whose tick is not later than the current
tick out of the list and hands it over. When injection starts in tick 10, the events of ticks 1 to
10 all come at once.

The time to live of an injected event counts from the upload of the list. If the tick of an event comes later than its
time to live allows, the event has already expired when it is handed over. The state
machines never see such an event. For a long list, set the time to live of the environment to 0 so that no event
expires. Paths into `event` lead nowhere for injected events, because these carry their payload only as text.

A client uploads a list with one press in tick 3 and starts the injection.

```bash
curl -X POST "http://127.0.0.1:8080/sendMessageToFeature?envKey=env-1763035112345&featureName=EventInjection" \
  -d 'upload:{"3": [{"environmentKey": "switch", "messageType": "press", "payload": ""}]}'
curl -X POST "http://127.0.0.1:8080/sendMessageToFeature?envKey=env-1763035112345&featureName=EventInjection" -d "start"
```

```text
successfully uploaded events
injection started
```

## 3.2.8 EventReplayController

EventReplayController replays a recording through EventRecording and EventInjection. Switching it on switches both of
them on as well.

| Message | Answer | What happens |
|---|---|---|
| `initialize` | `replay successfully initialized` | Stops recording and injection and uploads the recording as the list of EventInjection |

Any other message gets the answer `invalid message: <message>`. If the upload of the recording fails, the call is
refused with an error status and the reason as text. Recording and injection are stopped by then.

A replay in the environment that was recorded cannot hit the same ticks again. As
[3.1.13.9 Stop and start, forcing and clients](3.1-execution-semantics.md#31139-stop-and-start-forcing-and-clients)
explains, a start after a stop continues the run with the next tick. Because the ticks of the recording lie in the past
by then, all recorded events come in the next tick after `initialize` and a start. A replay in the same ticks
as before takes a new environment and these steps.

1. Switch on EventRecording and send it `start`.
2. Start the environment and send events from a client.
3. Send `get` to EventRecording and keep the answer.
4. Create a new environment with the same uploads, switch on EventInjection, and send it `upload:` with the recording
   and then `start`.
5. Run and start the new environment. The events come in the same ticks as before, on the model as it was uploaded.

With TrueParallel off, the trace log of the replay equals the trace log of the recorded run line by line, apart from
the times and the key of the environment. That holds also when state machines are attached, exchanged and detached
and when they split and join, because the path numbers count the same way in both runs.

## 3.2.9 TrueParallel

Without TrueParallel, the branches of a split do their steps one after the other on the one thread of the
environment, in the order of the targets of the split that
[3.1.8 Splits and joins](3.1-execution-semantics.md#318-splits-and-joins) describes. Every run of the same model with
the same events then takes the same course.

With TrueParallel on, each branch gets a thread of its own when the split has fired and keeps it for as long as the
branch lives. In every tick all branches of a state machine do their steps at the same time on the shared model. The
tick ends when every branch has done its step. TickLimit, TickByTick, Breakpoint, EventRecording and EventInjection
count the ticks as before, because the ticks keep their numbers. The active states are reported once per tick, after
all steps. A join is still tried before the branches step. A branch that waits for Python in an `EVAL` holds up only
itself until the end of the tick. Each branch that calls Python at the same time as another one gets a Python process
of its own.

A switch of TrueParallel, such as this one, takes effect only at the start of the next tick.

```bash
curl -X POST "http://127.0.0.1:8080/activateFeature?envKey=env-1763035112345&featureName=TrueParallel"
```

The thread of a branch ends when a join merges the branches, when the environment stops, or at the end of the tick in
which TrueParallel was switched off. A start after a stop gives the branches new threads at their next step. If the
environment is stopped while a branch waits at a breakpoint, the threads of the halted tick stay until that tick ends.
The feature neither touches state machines without a split nor runs the several state machines of an environment at
the same time. They still do their steps one after the other.

### 3.2.9.1 What a modeler can rely on

- Each single action is atomic. One `SET`, `APPEND`, `SETLIST`, `DROPLIST`, `SETOBJ`, `APPENDOBJ`, `DROPOBJ` or
  `EVENT` changes the model or the event bus in one go. No other branch sees it half done.
- An action that computes its value first reads and then writes. Between the read and the write another branch
  can write. Two branches that increment the same number with `SET("count", EVAL { return $(count) + 1 })` can
  lose an increment.
- Two branches that write the same property race. Which value stays is not defined.
- The order of actions across branches is not defined. Within one branch the actions run in their order, as always.
- The rule of [3.1.5.1 Blocks and errors](3.1-execution-semantics.md#3151-blocks-and-errors) still holds: the changes
  of one ENTRY or DO block reach the clients together after the block. Blocks of different branches reach them in the
  order in which they ended. The revisions of the pushes still increase one by one.
- Events that one branch raises can be seen by another branch in the same tick or only in the next one.
- Branches that create, remove or exchange objects with state machines change the instances of the environment only
  at the end of the tick and all together, at the moment that
  [3.1.13.3 When instances join and leave](3.1-execution-semantics.md#31133-when-instances-join-and-leave) gives. An
  instance that a branch ends stops its other branches after the block they are in.
- With Breakpoint on, branches that reach breakpoints in the same tick halt one after the other. After a `resume`
  the waiting branch goes on and the next one halts. While one branch waits, the others finish their steps.

Leave TrueParallel off wherever a run must be deterministic, for example in tests and in replays with EventInjection.

In the trace log of [3.3.5 Trace log](3.3-running-the-runtime.md#335-trace-log), every line of a branch names the path
of the branch. With TrueParallel on, the lines of branches that step at the same time interleave in the order in which
they were written. The path tells them apart. The path numbers are the same as with TrueParallel off, because the
thread of the environment carries out splits, joins and exchanges in the same order either way.

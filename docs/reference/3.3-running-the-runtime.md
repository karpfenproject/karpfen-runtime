# 3.3 Running the runtime

The runtime is one program that listens for HTTP requests and WebSocket connections on one port, by default
`http://127.0.0.1:8080` and `ws://127.0.0.1:8080/ws`. It runs on your machine with Java or in a Docker container. The
IDE builds and starts the container itself, as [4.5 Running](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.5-running.md)
describes.

## 3.3.1 Requirements

| Way to run | Needs |
|---|---|
| On your machine | Java 21. Python 3 on the path as `python3`, `python` or `py` for state machines with Python code, with the packages that this code imports |
| In Docker | Docker. The image brings Java 21 and Python 3 with the packages `numpy`, `scipy`, `sympy`, `pandas`, `regex`, `python-dateutil` and `chardet` |

State machines whose `EVAL` blocks and macros the runtime computes itself need no Python, as
[3.1.6 EVAL and macros](3.1-execution-semantics.md#316-eval-and-macros) describes.

The runtime is built with the KStates, KMeta and KModel readers of karpfen-dsl-tools, which is a git submodule in the
folder `karpfen-dsl-tools`. Clone the repository with its submodule:

```bash
git clone --recurse-submodules https://github.com/karpfenproject/karpfen-runtime.git
cd karpfen-runtime
```

## 3.3.2 Running on your machine

The script `run_local.sh` builds the runtime and starts it from the folder of the repository:

```bash
./run_local.sh
```

The build runs without tests and ends in `build/install/karpfen-runtime/bin/karpfen-runtime`. The runtime reads
`application.conf` from the folder it starts in. To start it without the script, from the folder of the repository:

```bash
./gradlew installDist -x test
./build/install/karpfen-runtime/bin/karpfen-runtime
```

`./gradlew run` builds and starts the runtime in one step, also with `application.conf` from the folder of the
repository.

At the start the runtime prints the configuration it uses:

```text
[Main] Configuration loaded:
[Main]   Server: 127.0.0.1:8080
[Main]   WebSocket enabled: true
[Main]   Log level: INFO
[Main]   Engine tracing: false
[Main]   Default tick delay: 50ms
[Main]   Default event TTL: 3000ms
[Main]   Event consumption on fire: true
```

## 3.3.3 Running in Docker

The script `run_docker.sh` builds the image `karpfen-runtime` from the `Dockerfile` of the repository and runs it:

```bash
./run_docker.sh
./run_docker.sh /var/log/karpfen
```

The script hands the container a copy of `application.conf` in which `server.host` is `0.0.0.0`, so the runtime can be
reached from outside the container. It maps port 8080 of the container to port 8080 of your machine. When you change
`server.port`, change the port in the script too. The folder in the first argument, by default `logs` in the folder of
the repository, is mounted as `/app/logs` in the container. For trace logs on your machine, set
`engineTracing.tracingLogDirectory` to `/app/logs`. The container is removed when it ends.

The image has no `application.conf` of its own. A container started without one runs with the defaults of the table
below, and with `server.host` at `127.0.0.1` it cannot be reached from outside the container. To run the image without
the script, mount a configuration file at `/app/application.conf`:

```bash
docker build -t karpfen-runtime .
docker run --rm -p 8080:8080 -v "$PWD/docker.conf:/app/application.conf:ro" karpfen-runtime
```

## 3.3.4 Configuration

The runtime reads `application.conf` from the folder it starts in. Without the file it uses the defaults. The file has
one option per line in the form `name = value`, grouped in blocks:

```text
server {
  host = "127.0.0.1"
  port = 8080
}
engine {
  defaultTickDelayMs = 50
  defaultEventTtlMs  = 3000
}
```

The runtime finds an option by its name inside the block and does not look at the name of the block. A line that
starts with `#` is a comment, and so is text after `#` when two blanks or a tab stand before it. A value may stand in
quotes. A number that cannot be read gives the default. A boolean is `true` for `true` in any case and `false` for
anything else.

| Option | Default | In the shipped file | Meaning |
|---|---|---|---|
| `server.host` | `127.0.0.1` | `127.0.0.1` | The address the runtime listens on. `0.0.0.0` listens on all addresses |
| `server.port` | `8080` | `8080` | The port for HTTP and the WebSocket |
| `websocket.enabled` | `true` | `true` | With `false`, the runtime pushes no messages to WebSocket clients |
| `websocket.queueTimeoutMs` | `1000` | `1000` | Read and not used |
| `logging.level` | `INFO` | `INFO` | Printed at the start and not used |
| `logging.consoleOutput` | `true` | `false` | Read and not used |
| `engine.defaultTickDelayMs` | `1000` | `50` | The tick delay of an environment without `setTickDelay`, in milliseconds |
| `engine.defaultEventTtlMs` | `1000` | `3000` | The time to live of events in an environment without `setEventTtl`, in milliseconds. 0 means events never expire |
| `engine.eventConsumptionOnFire` | `true` | `true` | With `false`, an event that fires a transition is not consumed by it, as [3.1.7.3 Consumption](3.1-execution-semantics.md#3173-consumption) describes |
| `engineTracing.tracingEnabled` | `false` | `false` | With `true`, the runtime writes a trace log per environment |
| `engineTracing.tracingLogDirectory` | none | `logs` | The folder of the trace logs, relative to the folder the runtime starts in or absolute. Without it no trace file is written |
| `engineTracing.tracingConsoleOutput` | `false` | `false` | With `true` and tracing on, the runtime also prints every trace line |
| `engineTracing.simpleTrace` | `true` | `true` | Read and not used |

A tick delay of 0 lets an environment tick without any pause and keeps one processor core busy.

## 3.3.5 Trace log

With `engineTracing.tracingEnabled` set to `true`, the runtime writes one trace log per environment to
`<tracingLogDirectory>/engine-trace-<envKey>.log`. The file is opened when the environment is run and closed when the
runtime ends. A stop and a start of the environment go on writing to it.

Every line has the time, the key of the environment, the key of the object of the state machine or `*` for the whole
environment, the type of the entry, a message and details:

```text
[HH:mm:ss.SSS] [<envKey>] [<object>] <TYPE>: <message> | <name>=<value>, <name>=<value>
```

The beginning of the trace of the lamp:

```text
# Engine Trace Log — Engine: env-1763035112345 — Started: 2026-11-13T09:12:01.120Z
[10:12:01.125] [env-1763035112345] [lamp] INITIAL_STATE: Initial state stack: off | stack=off
[10:12:01.126] [env-1763035112345] [wallSwitch] INITIAL_STATE: Initial state stack: down | stack=down
[10:12:01.127] [env-1763035112345] [*] ENGINE_START: Engine started with 2 state machine(s), tickDelay=500ms
[10:12:01.128] [env-1763035112345] [lamp] TICK_START: Tick #1 | stack=off, currentStates=off, parallel=false
[10:12:01.129] [env-1763035112345] [lamp] STATE_ENTRY_EXEC: Executing onEntry for state 'off' | state=off, branch=env-1763035112345-lamp-b0, stack=off
[10:12:01.131] [env-1763035112345] [lamp] STATE_DO_SKIP: onDo for state 'off' is empty — skipped | state=off, branch=env-1763035112345-lamp-b0, stack=off
[10:12:01.131] [env-1763035112345] [lamp] TICK_END: Tick #1 completed | stack=off, currentStates=off, parallel=false
```

The types of entries:

| Type | Written when | Message |
|---|---|---|
| `INITIAL_STATE` | A state machine gets its start stack, or a client forces a state | `Initial state stack: on > full` or `Forced state: on > full` |
| `ENGINE_START` | The environment starts, or continues after a stop | `Engine started with 2 state machine(s), tickDelay=500ms` or `Engine continued after tick 42 with 2 state machine(s)` |
| `ENGINE_STOP` | The environment stops | `Engine stopped after 42 ticks` |
| `STATE_MACHINE_ATTACHED` | A state machine instance joins | `State machine 'glowing' attached`, or `State machine of the run configuration attached` for an attached state machine |
| `STATE_MACHINE_DETACHED` | A state machine instance leaves | `State machine 'glowing' detached` |
| `TICK_START` | A state machine begins its step | `Tick #3` |
| `TICK_END` | A state machine ends its step | `Tick #3 completed` |
| `STATE_ENTRY_EXEC` | An ENTRY block runs | `Executing onEntry for state 'on'` |
| `STATE_ENTRY_SKIP` | A state with an empty ENTRY block is entered | `onEntry for state 'on' is empty — skipped` |
| `STATE_DO_EXEC` | A DO block runs | `Executing onDo for state 'on'` |
| `STATE_DO_SKIP` | The innermost state has an empty DO block | `onDo for state 'on' is empty — skipped` |
| `TRANSITION_START` | A transition begins | `off -> full` |
| `TRANSITION_FIRED` | A transition changed the active states | `off -> full` |
| `TRANSITION_SKIPPED_LOOP` | A `NOT LOOPING` transition was skipped | `Skipped NOT LOOPING transition` |
| `SPLIT_START`, `SPLIT_FIRED` | A split begins and is done | `off -> test bulb,test switch` |
| `JOIN_START`, `JOIN_FIRED` | A join begins and is done | `bulb ok,switch ok -> on` |
| `ACTION_ERROR` | An action failed | `Error in onEntry for state 'off': <error>` |

The details of `TICK_START` and `TICK_END` are the stack, the innermost state of each branch and whether the state
machine has branches. The details of the entries of states name the state, the branch and its stack. The details of
transitions name the source and the target.

## 3.3.6 Stopping the runtime

Ctrl+C in the terminal of the runtime, or the end of the Docker container, stops it. The runtime closes the WebSocket
connections of all environments with code 1001 and the reason `Runtime stopped`, ends their engines with their Python
processes and trace logs, closes its server and ends. It keeps nothing: all environments, models and recordings are gone.

The runtime prints what it does on its console, also when tracing is off: environments that start and stop, clients
that register, payloads it cannot read, failed actions and failed `EVAL` clauses.

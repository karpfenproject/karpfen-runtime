# 3.3 Running the runtime

The runtime is one program that listens on one port for both HTTP requests and WebSocket connections, by default at
`http://127.0.0.1:8080` and `ws://127.0.0.1:8080/ws`. It runs on your machine with Java or in a Docker container.
How the IDE builds and starts the container on its own is described in
[4.5 Running](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.5-running.md).

The developer document
[Console and trace log of the runtime](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/console-and-trace.md)
on GitHub has examples of what the runtime prints on its console and of the lines it writes into a trace log.

## 3.3.1 Requirements

| Way to run | Needs |
|---|---|
| On your machine | Java 21. For state machines with Python code also Python 3 on the path as `python3`, `python` or `py`, with the packages that the code imports |
| In Docker | Docker. The image brings Java 21 and Python 3 with the packages `numpy`, `scipy`, `sympy`, `pandas`, `regex`, `python-dateutil` and `chardet` |

A state machine needs no Python when the runtime computes all its `EVAL` blocks and macros itself. Which code the
runtime computes without Python is explained in
[3.1.6.3 Where code runs](3.1-execution-semantics.md#3163-where-code-runs).

The runtime is built with the KStates, KMeta and KModel readers of karpfen-dsl-tools, a git submodule in the folder
`karpfen-dsl-tools`. For that reason the repository has to be cloned together with its submodule.

```bash
git clone --recurse-submodules https://github.com/karpfenproject/karpfen-runtime.git
cd karpfen-runtime
```

## 3.3.2 Running on your machine

The script `run_local.sh` builds the runtime without its tests and starts it in the folder of the repository.

```bash
./run_local.sh
```

The runtime reads `application.conf` from the folder it starts in. With the script that is the folder of the
repository, whose `application.conf` the runtime then uses. Without the script, the runtime is built into
`build/install/karpfen-runtime/bin/karpfen-runtime` and started from the folder of the repository with these two
commands.

```bash
./gradlew installDist -x test
./build/install/karpfen-runtime/bin/karpfen-runtime
```

`./gradlew run` builds and starts the runtime in one step and also reads `application.conf` from the folder of the
repository.

At the start the runtime prints on its console the values it uses for these options of
[3.3.4 Configuration](#334-configuration).

- `server.host` and `server.port`
- `websocket.enabled`
- `logging.level`
- `engineTracing.tracingEnabled`
- `engine.defaultTickDelayMs` and `engine.defaultEventTtlMs`
- `engine.eventConsumptionOnFire`
- `engine.resultCaching`, `engine.resultCacheMaxEntries` and `engine.resultCacheMaxMegabytes`

## 3.3.3 Running in Docker

The script `run_docker.sh` builds the image `karpfen-runtime` from the `Dockerfile` of the repository and runs it in a
container that is removed when it ends. Its optional argument is a folder for the trace logs.

```bash
./run_docker.sh
./run_docker.sh /var/log/karpfen
```

The script hands the container a copy of `application.conf` in which `server.host` is `0.0.0.0`, because a runtime
that listens only on `127.0.0.1` inside the container cannot be reached from outside it. The `application.conf` of
the repository stays as it is. The script maps port 8080 of the container to port
8080 of your machine without reading the port from the configuration. When you change `server.port`, change the port
in the script too.

The folder in the first argument is mounted as `/app/logs` in the container. Without an argument the script mounts the
folder `logs` of the repository. To get the trace logs on your machine, set `engineTracing.tracingLogDirectory` to
`/app/logs`.

The image has no `application.conf` of its own. A container started without one runs with the defaults of the table
in 3.3.4. With the default `127.0.0.1` for `server.host` it cannot be reached from outside the container. To
run the image without the script, mount a configuration file with `server.host` at `0.0.0.0` as
`/app/application.conf`. In this example the file is `docker.conf` in the current folder.

```bash
docker build -t karpfen-runtime .
docker run --rm -p 8080:8080 -v "$PWD/docker.conf:/app/application.conf:ro" karpfen-runtime
```

## 3.3.4 Configuration

The runtime reads `application.conf` from the folder it starts in and uses the defaults when there is no such file.
The file has one option per line in the form `name = value`, grouped in blocks.

```text
server {
  host = "127.0.0.1"
  port = 8080
}
engine {
  defaultTickDelayMs = 50
  defaultEventTtlMs  = 3000
}
```

The runtime reads the file by these rules.

- It finds an option by its name alone and does not look at the name of the block around it.
- A line that starts with `#` is a comment. So is the text after a `#` that has two blanks or a tab in front of it.
- A value may stand in quotes.
- A number that cannot be read gives the default.
- A boolean is `true` for the word `true` in any case of its letters and `false` for anything else.

| Option | Default | In the shipped file | Meaning |
|---|---|---|---|
| `server.host` | `127.0.0.1` | `127.0.0.1` | The address the runtime listens on. `0.0.0.0` listens on all addresses |
| `server.port` | `8080` | `8080` | The port for HTTP and the WebSocket |
| `websocket.enabled` | `true` | `true` | With `false`, the runtime pushes no messages to WebSocket clients |
| `websocket.queueTimeoutMs` | `1000` | `1000` | Read and not used |
| `logging.level` | `INFO` | `INFO` | Printed at the start and not used |
| `logging.consoleOutput` | `true` | `false` | Read and not used |
| `engine.defaultTickDelayMs` | `1000` | `50` | The tick delay of an environment without `setTickDelay`, in milliseconds |
| `engine.defaultEventTtlMs` | `1000` | `3000` | The time to live of events in an environment without `setEventTtl`, in milliseconds. 0 means that events never expire |
| `engine.eventConsumptionOnFire` | `true` | `true` | With `false`, an event that fires a transition is not consumed by it. The rules are in [3.1.7.3 Consumption](3.1-execution-semantics.md#3173-consumption) |
| `engine.resultCaching` | `true` | `true` | With `false`, an environment without `setResultCaching` answers no code from the result cache of [3.1.6.6 The result cache](3.1-execution-semantics.md#3166-the-result-cache) |
| `engine.resultCacheMaxEntries` | `10000` | `10000` | The most results the cache of one environment holds. A value below 1 gives the default |
| `engine.resultCacheMaxMegabytes` | `64` | `64` | The most memory the results of the cache of one environment may take, in megabytes. A value below 1 gives the default |
| `engine.allowProcessCalls` | `false` | `false` | With `true`, code may make the uses that start a process or run code by another way, which [3.1.6.3 Where code runs](3.1-execution-semantics.md#3163-where-code-runs) lists and refuses by default |
| `engineTracing.tracingEnabled` | `false` | `false` | With `true`, the runtime writes a trace log per environment |
| `engineTracing.tracingLogDirectory` | none | `logs` | The folder of the trace logs, relative to the folder the runtime starts in or absolute. Without it no trace file is written |
| `engineTracing.tracingConsoleOutput` | `false` | `false` | With `true` and tracing on, the runtime also prints every trace line |
| `engineTracing.simpleTrace` | `true` | `true` | Read and not used |

A tick delay of 0 lets an environment tick without any pause and keeps one processor core busy.

## 3.3.5 Trace log

With `engineTracing.tracingEnabled` set to `true`, the runtime writes one trace log per environment to
`<tracingLogDirectory>/engine-trace-<envKey>.log`. The file is opened when the environment is run and closed when the
environment is dropped or the runtime ends. After a stop and a start of the environment the log
goes on in the same file.

The file begins with a header line that names the environment and the moment the log was started. Every further line
holds the time, the key of the environment, the key of the object whose state machine it is about or `*` for the
whole environment, the type of the entry, a message and details. Its form is
`[HH:mm:ss.SSS] [<envKey>] [<object>] <TYPE>: <message> | <name>=<value>, <name>=<value>`.

| Type | Written when | Message |
|---|---|---|
| `INITIAL_STATE` | A state machine gets its start stack, right after it is attached or exchanged, or a client forces a state | `Initial state stack: on > full` or `Forced state: on > full` |
| `ENGINE_START` | The environment starts, or continues after a stop | `Engine started with 2 state machine(s), tickDelay=500ms` or `Engine continued after tick 42 with 2 state machine(s)` |
| `ENGINE_STOP` | The environment stops | `Engine stopped after 42 ticks` |
| `STATE_MACHINE_ATTACHED` | A state machine instance joins on an object without one | `State machine 'glowing' attached`, or `State machine of the run configuration attached` for an attached state machine |
| `STATE_MACHINE_DETACHED` | A state machine instance leaves and no other takes its place | `State machine 'glowing' detached` |
| `STATE_MACHINE_EXCHANGED` | `EXCHANGE` ended the instance on an object and started another one in its place | `State machine 'glowing' exchanged for 'blinking'`, or `State machine of the run configuration exchanged for 'blinking'` |
| `TICK_START` | A state machine begins its step | `Tick #3` |
| `TICK_END` | A state machine ends its step | `Tick #3 completed` |
| `STATE_ENTRY_EXEC` | An ENTRY block runs | `Executing onEntry for state 'on'` |
| `STATE_ENTRY_SKIP` | A state with an empty ENTRY block is entered | `onEntry for state 'on' is empty — skipped` |
| `STATE_DO_EXEC` | A DO block runs | `Executing onDo for state 'on'` |
| `STATE_DO_SKIP` | The innermost state has an empty DO block | `onDo for state 'on' is empty — skipped` |
| `TRANSITION_START` | A transition begins | `off -> full` |
| `TRANSITION_FIRED` | A transition changed the active states | `off -> full` |
| `TRANSITION_SKIPPED_LOOP` | A `NOT LOOPING` transition was skipped | `Skipped NOT LOOPING transition` |
| `SPLIT_START`, `SPLIT_FIRED` | A split begins and is done | `off -> test bulb,test switch` |
| `JOIN_START`, `JOIN_FIRED` | A join begins and is done | `bulb ok,switch ok -> on` |
| `ACTION_ERROR` | An action failed | `Error in onEntry for state 'off': <error>` |
| `CONDITION_ERROR` | A clause of a condition failed and counts as false | `Error in a condition of a transition from 'off': <error>` |

Every entry about a state machine names a path. A path is one stretch of the state machine on an object that a single
branch runs from its beginning to its end. The object and the path number together name exactly one stretch, because
path numbers count per object from 0 and are never given twice while the environment lives. Grouping the lines by
object and path separates them all, also the lines of branches that interleave while the feature TrueParallel is on.

The first state machine on an object runs on path 0. A new path starts in each of these cases.

- Each target of a split starts a new path.
- A join ends the paths of the split and starts one more.
- A forced state ends the current paths and starts one more.
- A state machine that `EXCHANGE` or a later attachment brings to the same object starts with the next number.

A stop and a start keep the paths.

The details of a type appear in the order given in this table.

| Type | Details |
|---|---|
| `STATE_MACHINE_ATTACHED` | `stateMachine` (the name, empty for a state machine of the run configuration), `path` |
| `STATE_MACHINE_DETACHED` | `stateMachine`, then `path`, or `paths` while the state machine is split |
| `STATE_MACHINE_EXCHANGED` | `ended` (the name of the state machine that ended, empty for one of the run configuration), `started`, `ends` (the paths that ended), `path` (the path of the new state machine) |
| `INITIAL_STATE` | `path`, `stack`. After a forced state `ends` comes first, with the paths the force ended |
| `TICK_START`, `TICK_END` | `path`, or `paths` while the state machine is split. Then `stack` (the active states of all branches), `currentStates` (the innermost state of each branch, in the order of `paths`), `parallel` |
| entries of states | `path`, `state`, `stack` (the stack of the branch) |
| `TRANSITION_START`, `TRANSITION_FIRED` | `path`, `from`, `to`, `stack` |
| `TRANSITION_SKIPPED_LOOP` | `path`, `stack` |
| `SPLIT_START` | `path`, `from`, `to` |
| `SPLIT_FIRED` | `path` (the path that splits), `starts` (the new paths, in the order of the targets), `from`, `to` |
| `JOIN_START` | `paths` (the paths about to be joined), `from`, `to` |
| `JOIN_FIRED` | `ends` (the joined paths), `path` (the new path), `from`, `to` |
| `ACTION_ERROR` | `path`, `state`, `stack` |
| `CONDITION_ERROR` | `path`, `state` (the state the transition leaves), `stack`. For a join `paths` (the paths it would join) and `state` (its source states) |

A detail that lists several paths separates them with commas. The entries of the whole environment, under `*`, name
no path. A line about a state machine as it stands names `path`, or `paths` while the state machine is split. A line
that changes the paths names those it ends in `ends` and those it starts in `starts` or `path`.

Take a lamp on path 0 that tests its bulb and its switch in two branches and joins them in `on`. Its `SPLIT_FIRED`
line names `starts=1,2` because the two branches run on the paths 1 and 2. While they run, `TICK_END` names
`paths=1,2` and `parallel=true`. The `JOIN_FIRED` line names `ends=1,2` and `path=3`. All lines about `on` after it
are written on path 3.

When the state machine `glowing` of the bulb runs on path 0 and is exchanged for `blinking`, the exchange takes one
line, `STATE_MACHINE_EXCHANGED` with `ended=glowing`, `started=blinking`, `ends=0` and `path=1`. An `INITIAL_STATE`
line with the start stack of the new state machine on path 1 follows it.

Two exchanges of one object in the same tick write one line. It names the state machine that ran before the tick and
the one named last. `EXCHANGE` on an object without a state machine writes `STATE_MACHINE_ATTACHED`. Over the
WebSocket, a client that observes the state machines still gets two messages for an exchange,
`stateMachineDetached` and then `stateMachineAttached`. Their form is given under
[stateMachineAttached and stateMachineDetached](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/websocket.md#statemachineattached-and-statemachinedetached)
in the developer document on the WebSocket.

## 3.3.6 Stopping the runtime

The runtime stops on Ctrl+C in its terminal and also when its Docker container ends. Before it ends, it closes the
WebSocket connections of every environment that was run with code 1001 and the reason `Runtime stopped`. It ends the
engines of these environments together with their Python processes and trace logs and then closes its server. A
client of an environment that was never run gets no such close and just loses its connection when the server stops.
Nothing is kept: all environments, models and recordings are gone.

A single environment ends for good with `POST /dropEnvironment` of the
[HTTP API](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/http-api.md#environments),
while the runtime goes on. The connections of the environment close with code 1000 and the reason
`Environment dropped`. Its trace file stays in the trace directory. Clients of a runtime that runs for a long time and
serves many runs should drop the environments they no longer need, because a stopped environment keeps its
model, its engine and its Python processes in memory until it is dropped.

Also when tracing is off, the runtime prints what it does on its console. Among other things it prints a line for each
of the following.

- an environment that starts or stops
- a client that registers
- a payload it cannot read
- a failed action or a failed `EVAL` clause
